2.3 RECURRING INVOICES (New Tab: "Recurring")
──────────────────────────────────────────────

DB Table: recurring_invoice_configs
  id               UUID          PK DEFAULT gen_random_uuid()
  template_id      UUID          REFERENCES invoice_templates(id)
  client_id        UUID          REFERENCES clients(id) NOT NULL
  frequency        TEXT          NOT NULL
                                 CHECK IN ('weekly','monthly','quarterly',
                                           'annually')
  start_date       DATE          NOT NULL
  end_date         DATE          -- nullable; null = runs indefinitely
  next_run_date    DATE          NOT NULL
  auto_send        BOOLEAN       DEFAULT false
  status           TEXT          DEFAULT 'active'
                                 CHECK IN ('active','paused','completed')
  created_by       UUID          REFERENCES auth.users(id)
  created_at       TIMESTAMPTZ   DEFAULT now()

Supabase Edge Function: process-recurring-invoices
  Schedule: daily at 00:30 IST via pg_cron or Supabase cron.
  Logic:
    SELECT * FROM recurring_invoice_configs
      WHERE status = 'active' AND next_run_date <= CURRENT_DATE;
    For each config:
      1. Create invoice record (clone template line items; set client, dates,
         invoice_number per policy format, status = 'Draft').
      2. If auto_send = true: POST to send-invoice function → status = 'Sent'.
      3. Compute next_run_date based on frequency:
           weekly    → next_run_date + 7 days
           monthly   → next_run_date + 1 month (same day)
           quarterly → next_run_date + 3 months
           annually  → next_run_date + 1 year
      4. If end_date set and new next_run_date > end_date:
           UPDATE status = 'completed'.
      5. INSERT notification (recurring_invoice_created).

Recurring Tab UI:
  Table: Client | Template | Frequency | Start Date | End Date | Next Run |
         Auto-Send | Status | Actions [Pause/Resume][Edit][Delete].
  [+ New Recurring Config] button → <RecurringConfigModal>:
    Client picker | Template picker (optional) | Frequency radio |
    Start Date | End Date (optional) | [Auto-Send?] toggle.

Create Tab — "Make Recurring" Toggle:
  Below standard invoice fields: [🔄 Make this a recurring invoice] toggle.
  When toggled ON: reveals Frequency / Start Date / End Date / Auto-Send fields.
  On Save: creates both the invoice AND a recurring_invoice_config record.

Invoice List: Recurring invoices show indigo "🔄 Recurring" badge in
  Invoice # column.

  total_paid = SUM(amount) FROM invoice_payments WHERE invoice_id = NEW.invoice_id;

2.6 GST / TAX SUPPORT (Indian Context)
────────────────────────────────────────

invoice_items additions:
  hsn_code         TEXT          -- HSN (goods) or SAC (services) code
  gst_rate         NUMERIC(4,1)  DEFAULT 18.0
                                 CHECK IN (0, 5, 12, 18, 28)
  cgst_amount      NUMERIC(12,2) GENERATED ALWAYS AS (
                     CASE WHEN supply_type = 'intrastate'
                          THEN (amount * gst_rate / 200) ELSE 0 END
                   ) STORED   -- computed on invoice level, stored here
  sgst_amount      NUMERIC(12,2) -- same as cgst_amount for intrastate
  igst_amount      NUMERIC(12,2) GENERATED ALWAYS AS (
                     CASE WHEN supply_type = 'interstate'
                          THEN (amount * gst_rate / 100) ELSE 0 END
                   ) STORED

  NOTE: supply_type is on the parent invoices row; GENERATED columns
  reference it via a DB view or are computed in application code at
  save-time and stored as regular columns (simpler approach recommended).

invoices additions:
  supply_type      TEXT          CHECK IN ('interstate','intrastate')
  place_of_supply  TEXT          -- 2-digit state code e.g. '27' Maharashtra

Auto-calculate logic (frontend + confirmed on save):
  IF supply_type = 'interstate':
    item.igst_amount = item.amount * item.gst_rate / 100
    item.cgst_amount = 0; item.sgst_amount = 0
  ELSE (intrastate):
    item.cgst_amount = item.sgst_amount = item.amount * item.gst_rate / 200
    item.igst_amount = 0

GST Invoice Format (UI + PDF):
  Invoice header section:
    Left: company name, address, GSTIN, PAN, state code.
    Right: "TAX INVOICE" heading, Invoice No., Invoice Date, Due Date.
  Bill To:  Client name, address, GSTIN, PAN.
  Line items table columns:
    # | Description | HSN/SAC | Qty | Unit | Rate | Taxable Value | GST% |
    CGST | SGST | IGST | Total
  Tax summary table (below line items):
    HSN/SAC | Taxable Value | CGST Rate | CGST Amt | SGST Rate | SGST Amt |
    IGST Rate | IGST Amt | Total Tax
  Totals: Taxable Amount | Total CGST | Total SGST | Total IGST | Grand Total.
  Grand Total in words (Indian numbering: Lakhs, Crores).
  Bank details for payment (from INVOICE_POLICIES.company_details).

[Download GST Invoice PDF] button:
  Uses @react-pdf/renderer or jsPDF + html2canvas.
  Format: A4 portrait, 15mm margins.
  Filename: {invoice_number}_{client_name}_{date}.pdf

2.7 OVERDUE MANAGEMENT
───────────────────────

Auto-Overdue Edge Function (run daily, same cron as recurring):
  UPDATE invoices
    SET status = 'Overdue'
  WHERE due_date < CURRENT_DATE
    AND status IN ('Sent', 'Partially Paid');

Overdue Reminder Emails:
  Check INVOICE_POLICIES.overdue_reminder_days (e.g. [1, 7, 14]).
  For each overdue invoice, if (CURRENT_DATE - due_date) IN reminder_days
    AND no reminder already sent for that day interval:
    → Send reminder email to client.
    → Log in invoice_reminder_log table (invoice_id, reminder_day, sent_at).

Late Fee:
  INVOICE_POLICIES.late_fee_percent_per_month (e.g. 2.0).
  If late_fee > 0 and invoice overdue > 30 days:
    Add a "Late Fee" line item (automatically, or prompt Finance to add).
  Late fee amount = balance_due × (late_fee_percent / 100) × (months_overdue).

Invoice List: Overdue rows styled with bg-red-50; due date cell shows
  "Overdue {N}d" in red badge with subtle pulse animation.

Analytics — Overdue Aging Report:
  Bar chart + table: Outstanding grouped by age buckets:
    0-30 days | 31-60 days | 61-90 days | 90+ days
  Drill-down: click bucket → filtered invoice list for that bucket.

SECTION 5 — VALIDATION RULES
--------------------------------------------------------------------------------

Invoice Number:
  Auto-generated per INVOICE_POLICIES.invoice_number_format on first save.
  Immutable once the invoice exits Draft status.
  Sequence stored in a DB sequence or a counter row in app_settings.

Client:
  Required; must be is_active = true.
  If client deactivated after invoice creation, invoice remains valid
  (historical record preserved).

Line Items:
  Minimum 1 line item required.
  description: required, max 500 chars.
  quantity: required, > 0, up to 6 decimal places.
  rate: required, >= 0 (zero-rate line items allowed for free items).
  gst_rate: must be from GST_TAX_RATES (0/5/12/18/28).
  hsn_code: recommended; warning shown if absent (not blocking).

Dates:
  invoice_date: defaults to today; can be backdated (Finance role).
  due_date: must be >= invoice_date.

Paid Invoice Editing:
  Cannot edit a Paid invoice. Actions available: [View] [Cancel with Reason].
  Cancel creates a credit note reference (credit_note_reference field).
  Cancellation requires Finance Manager role + mandatory cancel_reason.

Delete Rules:
  Cannot delete Paid or Overdue invoices.
  Paid → Cancel only (with credit note reference).
  Overdue → Cancel only (with reason).
  Draft / Sent → Delete allowed (Finance role), permanently removed.

Recurring Config:
  start_date >= today (cannot create recurring configs for past dates).
  end_date, if provided: must be > start_date.
  end_date, if provided: must be > today at creation time.

Payment Recording:
  amount > 0 (positive only).
  amount <= balance_due is recommended; if amount > balance_due:
    warning modal: "Amount ₹{X} exceeds outstanding balance ₹{balance_due}.
    This will record an overpayment. Continue?"
    [Cancel] [Record Overpayment]

GST Validation:
  If company_gstin set: supply_type is required on invoice.
  If supply_type = 'interstate': igst applies; cgst/sgst must be 0.
  If supply_type = 'intrastate': cgst + sgst applies; igst must be 0.
  place_of_supply: required if supply_type set; must be valid 2-digit state code.

SECTION 7 — PUSH NOTIFICATIONS (Web Push API / VAPID)
--------------------------------------------------------------------------------

All notifications stored in notifications table AND pushed via Web Push API.
Recipient resolution uses Permissions App role membership.

Event: invoice_sent
  Recipients : users with role 'finance' + 'admin'
  Type       : info
  Title      : "Invoice Sent"
  Body       : "Invoice {invoice_number} sent to {client.name} for
                ₹{formatted_total}"
  Action URL : /invoices/{id}

Event: invoice_paid
  Recipients : users with role 'finance' + invoice created_by user
  Type       : success
  Title      : "Invoice Paid"
  Body       : "Invoice {invoice_number} paid by {client.name} — ₹{total}"
  Action URL : /invoices/{id}

Event: invoice_overdue
  Recipients : users with role 'finance' + 'admin'
  Type       : warning
  Title      : "Invoice Overdue"
  Body       : "Invoice {invoice_number} from {client.name} is overdue by
                {overdue_days} days — ₹{balance_due} outstanding"
  Action URL : /invoices/{id}

Event: invoice_overdue_14d
  Recipients : users with role 'finance'
  Type       : urgent-warning
  Title      : "Invoice Overdue 14+ Days"
  Body       : "Invoice {invoice_number} overdue 14+ days — consider escalation"
  Action URL : /invoices/{id}

Event: partial_payment_received
  Recipients : users with role 'finance'
  Type       : info
  Title      : "Partial Payment Received"
  Body       : "{client.name} made partial payment ₹{payment.amount} on
                Invoice {invoice_number}"
  Action URL : /invoices/{id}

Event: recurring_invoice_created
  Recipients : users with role 'finance'
  Type       : info
  Title      : "Recurring Invoice Created"
  Body       : "Recurring invoice {invoice_number} auto-created for {client.name}"
  Action URL : /invoices/{id}

Event: invoice_cancelled
  Recipients : users with role 'finance'
  Type       : info
  Title      : "Invoice Cancelled"
  Body       : "Invoice {invoice_number} cancelled by {cancelled_by.name}"
  Action URL : /invoices/{id}

Push delivery:
  Edge Function send-push-notification receives { user_ids[], event, payload }.
  Fetches push_subscriptions for each user_id from push_subscriptions table.
  Calls web-push library with VAPID keys.
  Falls back gracefully if subscription expired (removes stale record).

G2 — PF CAP AT ₹1,800/MONTH
  Problem: PF calculated on full basic salary with no ceiling.
  Fix (in payroll processing function):

    const PF_WAGE_CEILING = 15000;    // statutory ceiling per EPFO
    const PF_RATE = 0.12;             // 12% employee contribution
    const EMPLOYER_PF_RATE = 0.12;    // 12% employer contribution

    const pfBase = Math.min(employee.basicSalary, PF_WAGE_CEILING);
    const pfEmployee = Math.round(pfBase * PF_RATE);     // max ₹1,800
    const pfEmployer = Math.round(pfBase * EMPLOYER_PF_RATE); // max ₹1,800

    // ESI: 0.75% employee, 3.25% employer on gross <= ₹21,000
    const ESI_GROSS_LIMIT = 21000;
    const ESI_EMPLOYEE_RATE = 0.0075;
    const ESI_EMPLOYER_RATE = 0.0325;
    const esiEmployee = employee.grossSalary <= ESI_GROSS_LIMIT
      ? Math.round(employee.grossSalary * ESI_EMPLOYEE_RATE)
      : 0;
    const esiEmployer = employee.grossSalary <= ESI_GROSS_LIMIT
      ? Math.round(employee.grossSalary * ESI_EMPLOYER_RATE)
      : 0;

  Both ceiling values configurable in PAYROLL_POLICIES Master Data.

G4 — TDS PROPER CALCULATION
  Problem: Flat 10% TDS applied; no standard deduction, HRA, or slab-based
  computation.

  Full TDS calculation (new tax regime, FY 2025-26):

    Step 1: Annual gross = salary_structure.monthly_ctc × 12
    Step 2: Standard deduction = ₹75,000 (new regime) OR ₹50,000 (old regime)
            Read from PAYROLL_POLICIES.standard_deduction
    Step 3: HRA Exemption (OLD REGIME ONLY):
              min of:
                a) Actual HRA received (from salary component)
                b) 50% of basic salary (metro city) or 40% (non-metro)
                c) Actual rent paid − 10% of basic salary
              (Requires rent_paid_monthly from employee HRA declaration)
    Step 4: Other declared investments (80C, 80D, NPS etc.) — old regime only
              = salary_structure.declared_other_investments (sum JSONB)
    Step 5: Taxable income = gross − standard_deduction
              (old regime: also subtract HRA exemption + other investments)
    Step 6: Apply tax slabs (new regime FY 2025-26):
              ₹0 – ₹3,00,000         →  0%
              ₹3,00,001 – ₹7,00,000  →  5%
              ₹7,00,001 – ₹10,00,000 →  10%
              ₹10,00,001 – ₹12,00,000 → 15%
              ₹12,00,001 – ₹15,00,000 → 20%
              > ₹15,00,000            →  30%
    Step 7: Add 4% Health & Education Cess on tax amount
    Step 8: Subtract rebate under 87A (if taxable income <= ₹7,00,000
              and new regime: full tax rebate, annual tax = 0)
    Step 9: Monthly TDS = annual_tax / 12 (integer, rounded up)
    Step 10: December adjustment — recalculate full-year TDS; adjust
               December deduction to reconcile any rounding drift.
    Store tds_calculation_details JSONB on payroll_record:
    {
      "regime": "new",
      "annual_gross": 1200000,
      "standard_deduction": 75000,
      "hra_exemption": 0,
      "other_deductions": 0,
      "taxable_income": 1125000,
      "slab_breakdowns": [
        {"from":0,"to":300000,"rate":0,"tax":0},
        {"from":300001,"to":700000,"rate":5,"tax":20000},
        ...
      ],
      "base_tax": 82500,
      "cess": 3300,
      "rebate_87a": 0,
      "annual_tds": 85800,
      "monthly_tds": 7150
    }

G8 — LOP DEDUCTION INTEGRATION

    SELECT employee_id, COUNT(*) as lop_days

      AND status = 'approved'
      AND leave_date >= :period_start
      AND leave_date <= :period_end

    const WORKING_DAYS_PER_MONTH = 30; // configurable in PAYROLL_POLICIES

    ₹12,00,001 – ₹15,00,000 → 20%
    > ₹15,00,000            → 30%
  Seeded for regime=old, financial_year=2025-26:
    ₹0 – ₹2,50,000          → 0%
    ₹2,50,001 – ₹5,00,000   → 5%
    ₹5,00,001 – ₹10,00,000  → 20%
    > ₹10,00,000             → 30%

Group: BANK_TEMPLATES
  (Seeded entries per Section 2.5)

SECTION 5 — VALIDATION RULES
--------------------------------------------------------------------------------

Payroll Processing Lock:
  Cannot run process-payroll if a non-nullified lock exists for the
    target month/year.
  Error message (UI banner): "Payroll for {Month} {Year} is locked.
    Finance Manager can unlock to re-process."

Individual Record Approval:
  Cannot approve individual payroll records if the month's overall run
    is not in 'processing' state (prevents approving records for a month
    that hasn't been processed yet).

Salary Structure:
  Basic salary must be >= 40% of CTC.
    (Statutory requirement; validation error on save if violated.)
  basic_salary + allowances + employer_pf + employer_esi should reconcile
    to CTC ± ₹100 rounding tolerance.

HRA Declaration:
  hra_declaration (rent paid) must be <= 12 × actual HRA component received.
  For annual rent > ₹1,00,000: UI shows warning "Attach rent receipts for
    amounts exceeding ₹1L/year" (non-blocking — advisory).

TDS:
  Monthly TDS cannot be negative.
    If computed TDS < 0 (due to deduction declarations): set TDS = 0.
    Payslip shows: "TDS: ₹0 (Income below taxable threshold)".
  tds_override requires mandatory override_reason field.

LOP Days:
  lop_days for a given employee in a month cannot exceed the total number
    of calendar working days in that month.
  If lop_days > working_days: validation error "LOP days ({X}) cannot
    exceed working days ({Y}) in {Month}."

NEFT Export:
  Can only export records with status = 'approved'.
  All employees in the export must have non-null bank_account_number and
    bank_ifsc in salary_structures.
  Pre-export check lists employees with missing bank details.

Salary Revision:
  effective_from cannot be a date within a locked pay period (month locked
    and not unlocked).
  Error: "Effective date {date} falls in a locked payroll period ({Month}
    {Year}). Unlock payroll first or choose a future date."
  new_ctc and new_basic must both be > 0.
  new_basic >= 40% of new_ctc (same statutory rule as salary structure).

PF Voluntary:
  If employee opts for higher voluntary PF (> 12% of basic):
    employer share remains capped at statutory 12% of min(basic, 15000).
    voluntary excess is employee-only and should be clearly labelled.

SECTION 6 — CROSS-APP INTEGRATIONS
--------------------------------------------------------------------------------

Payroll ↔ Employee Directory:
  salary_structures.employee_id FK to employees(id).
  On employee deactivation (Employee Directory): trigger sets
    salary_structures.is_active = false; future payroll runs skip the employee.
  New employee onboarding flow prompts to create salary structure.

Payroll ↔ Employee Dashboard:
  Employee Dashboard Payslip tab:
    SELECT * FROM payroll_records WHERE employee_id = auth.uid()
      ORDER BY pay_period_start DESC;
  Employee cannot see other employees' records (RLS: employee_id = auth.uid()).

Payroll → Executive Dashboard:
  View exec_dashboard_payroll_kpis:
    - Monthly total payroll cost (gross + employer contributions)
    - Headcount trend
    - Average salary
    - Salary cost as % of revenue (joined with Invoice data)
  Exec Finance tab reads from this view.

Payroll → Analytics:
  Analytics Finance tab: payroll trend, department-wise cost breakdown,
    PF/ESI contribution summary.

Payroll ↔ Leave Management:
  LOP deduction integration reads from leaves table (per G8 fix).
  RPC function: get_lop_days(employee_id, period_start, period_end)
    → returns count of approved LOP leave days.

Payroll → Security (Audit Log):
  Events logged to audit_events:
    payroll_processed, payroll_approved, payroll_locked, payroll_unlocked,
    salary_structure_updated, salary_revision_submitted,
    salary_revision_approved, salary_revision_rejected,
    tds_override_applied, neft_file_downloaded.

Payroll → Workflow Automation:
  salary_revision_submitted → triggers "Salary Revision Approval" workflow.
  Workflow steps: notify approver → wait for approve/reject →
    if approved: apply revision + notify employee + HR →
    if rejected: notify submitter + reason.
  payroll_lock/unlock events logged in workflow audit trail.

Payroll → Invoice:
  Contractor employees: payroll record can link to invoice_id.
  Bidirectional: invoice.contractor_employee_id can reference employee.

Payroll → Notifications Bell:
  All SECTION 7 events also INSERT into notifications table.
