SECTION A3: CROSS-APP INTEGRATION MAP
================================================================================

Overview
--------
This section documents every automated, triggered, and workflow-driven
integration between the 10 apps in the HR Portal. Each integration entry
follows a standard format:

  - Source App → Target App
  - Trigger Event
  - Action Taken in Target
  - Data Passed
  - Sync Type
  - User Notification

Sync Type definitions:
  Automatic  — Fires without any user action; handled by database trigger,
                Supabase Edge Function, or background job.
  Triggered  — Fires when a user explicitly clicks a button or takes a
                deliberate UI action.
  Workflow   — Routed through the Workflow Automation app; requires one or
                more approval steps before the downstream action executes.

Notification delivery channels (used in entries below):
  in-app     — Notification Bell (real-time via Supabase Realtime websocket)
  email      — Transactional email via configured SMTP / Resend provider
  web push   — Browser push notification (service worker; opt-in)

INTEGRATION 1
Source App   : Recruitment
Target App   : Onboarding
--------------------------------------------------------------------------------
Trigger Event:
  Candidate record is marked as Hired — either by accepting a formal offer
  (offer_status = accepted) or by an HR user explicitly clicking the
  "Mark as Hired" action on the candidate profile.

Action Taken in Target:
  A new onboarding_record row is automatically created in the onboarding
  schema with status = Pre-boarding. The record is linked to the originating
  candidate via candidate_id. A pre-boarding portal link is generated and
  stored; it will be emailed to the new joiner separately via the Onboarding
  app's preboarding_link_sent event.

Data Passed:
  - candidate_id         → mapped to onboarding_record.candidate_ref
  - full_name            → onboarding_record.employee_name
  - personal_email       → onboarding_record.personal_email
  - position_title       → onboarding_record.designation
  - department_id        → onboarding_record.department_id
  - manager_id           → onboarding_record.reporting_manager_id
  - joining_date         → onboarding_record.joining_date
  - employment_type      → onboarding_record.employment_type
                           (Full-time | Part-time | Contract | Intern)

Sync Type    : Automatic
  Implemented as a Supabase database trigger (AFTER UPDATE on candidates
  WHERE NEW.status = 'hired') that calls an Edge Function
  onboarding_create_record().

User Notification:
  - HR Admin team (role = hr_admin):
      Channel  : in-app + email
      Title    : "New Joiner Record Created"
      Body     : "{full_name} has been marked as hired. Onboarding record
                  created — joining on {joining_date}."

  - Reporting Manager (manager_id):
      Channel  : in-app
      Title    : "New Team Member Joining"
      Body     : "{full_name} will be joining your team as {position_title}
                  on {joining_date}. Onboarding has been initiated."

INTEGRATION 2
Source App   : Onboarding
Target App   : Employee Directory
--------------------------------------------------------------------------------
Trigger Event:
  Onboarding record status transitions to Completed. This occurs when all
  mandatory checklist tasks (is_mandatory = true) in the onboarding_tasks
  table are marked done AND the HR owner clicks "Complete Onboarding" or an
  auto-complete background job detects all tasks are resolved.

Action Taken in Target:
  A new row is inserted into the employees table (Employee Directory schema),
  creating a fully populated employee profile. The employee is now searchable
  in the directory, visible in org charts, and eligible for all apps that
  depend on an employees record (Performance, Training, etc.).

Data Passed:
  - full_name            → employees.full_name
  - work_email           → employees.work_email
                           (assigned during onboarding, usually firstname.lastname@company.com)
  - personal_email       → employees.personal_email
  - department_id        → employees.department_id
  - designation          → employees.designation
  - reporting_manager_id → employees.reporting_manager_id
  - join_date            → employees.join_date
  - employment_type      → employees.employment_type
  - location_id          → employees.location_id
  - shift_id             → employees.shift_id
  - onboarding_id        → employees.onboarding_ref (audit trail link)

Sync Type    : Automatic
  Triggered by an AFTER UPDATE trigger on onboarding_records WHERE
  NEW.status = 'completed'. Calls Edge Function employee_directory_create().

User Notification:
  - HR Admin (role = hr_admin):
      Channel  : in-app
      Title    : "Employee Record Created"
      Body     : "{full_name}'s employee record has been created in the
                  directory. Employee ID: {employee_id}."

  - Reporting Manager:
      Channel  : in-app
      Title    : "Direct Report Added to Your Team"
      Body     : "{full_name} has completed onboarding and is now active in
                  the Employee Directory under your team."

INTEGRATION 3
Source App   : Onboarding
Target App   : User Management
--------------------------------------------------------------------------------
Trigger Event:
  HR user clicks the "Enable Access" button on the onboarding record detail
  page. This action is available once the joining_date is within 3 days or
  has passed, and the onboarding record is in Pre-boarding or In-Progress
  status.

Action Taken in Target:
  1. supabase.auth.admin.createUser() is called with the new joiner's
     work_email address, generating a Supabase Auth user entry.
  2. A corresponding app_users row is created in the user_management schema.
  3. The Employee role is assigned (role = employee).
  4. A Supabase Auth invitation email is dispatched (uses Supabase's built-in
     invite mechanism with a magic link that expires in 72 hours).
  5. The onboarding_record.access_enabled flag is set to true and
     access_enabled_at is stamped.

Data Passed:
  - work_email           → auth.users.email + app_users.email
  - full_name            → app_users.full_name
  - role                 → app_users.role = 'employee'
  - department_id        → app_users.department_id
  - onboarding_id        → app_users.onboarding_ref
  - employee_id          → app_users.employee_id (if directory record exists)

Sync Type    : Triggered (HR clicks "Enable Access")

User Notification:
  - New Employee (personal_email, since work account not yet active):
      Channel  : email (invitation email from Supabase Auth)
      Title    : "Welcome to {Company Name} — Activate Your Account"
      Body     : "Your HR portal access has been set up. Click the link
                  below to set your password and get started."
      Also     : in-app notification created for when they first log in:
                  "Welcome, {name}! Your account is active."

  - HR Admin (action performer):
      Channel  : in-app
      Title    : "Access Enabled"
      Body     : "System access has been enabled for {full_name}. Invitation
                  email sent to {work_email}."

INTEGRATION 4
Source App   : Onboarding
Target App   : IT Services (External)
--------------------------------------------------------------------------------
Trigger Event:
  Same trigger as Integration 3 — HR user clicks "Enable Access". This
  integration fires in parallel with the User Management call.

Action Taken in Target:
  An HTTP POST request is made to the IT Services API endpoint
  (configured in system settings as it_services_api_url). A hardware
  provisioning ticket is created for the new joiner with the following
  equipment items: Laptop, Mouse, Keyboard, Monitor. The ticket is assigned
  to the IT Admin group and due on the joining_date.

Data Passed:
  - ticket_title         : "Hardware Provisioning for New Joiner — {full_name}"
  - assignee_group       : "IT Admin"
  - due_date             : joining_date
  - priority             : "High"
  - custom_fields:
      - employee_name    : full_name
      - position         : designation
      - location         : location_name (resolved from location_id)
      - joining_date     : joining_date (ISO 8601)
      - department       : department_name
      - items_required   : ["Laptop", "Mouse", "Keyboard", "Monitor"]

Sync Type    : Triggered (fires on "Enable Access" click, parallel to INT-3)

User Notification:
  - IT Admin (role = it_admin):
      Channel  : in-app + email
      Title    : "New Hardware Provisioning Ticket"
      Body     : "A provisioning request has been raised for {full_name}
                  (joining {joining_date}, {location_name}).
                  Ticket: TKT-{ticket_id}."

  - HR Admin (action performer):
      Channel  : in-app
      Title    : "IT Ticket Created"
      Body     : "IT provisioning ticket TKT-{ticket_id} has been created
                  for {full_name}."

INTEGRATION 5
Source App   : Onboarding
Target App   : Training
--------------------------------------------------------------------------------
Trigger Event:
  Two conditions must both be true:
    a) onboarding_record.access_enabled = true
    b) The current date equals or exceeds onboarding_record.joining_date
  A daily background CRON job (runs at 06:00 UTC) checks for employees
  who meet both conditions and have not yet received their mandatory
  onboarding training enrollment.

Action Taken in Target:
  1. Queries the training catalogue for all courses flagged as
     is_mandatory_onboarding = true.
  2. Queries for additional role-specific mandatory courses matching the
     employee's designation or department.
  3. Creates training_enrollment records for each course with
     status = enrolled and due_date = joining_date + 30 days.
  4. Sets onboarding_record.training_enrolled = true to prevent
     re-processing.

Data Passed:
  - employee_id          → training_enrollments.employee_id
  - course_ids[]         → training_enrollments.course_id (one row per course)
  - due_date             : joining_date + 30 calendar days
  - enrollment_source    : 'onboarding_auto'
  - enrolled_by          : system (null user_id, system flag = true)

Sync Type    : Automatic (CRON-triggered background job on joining_date)

User Notification:
  - Employee:
      Channel  : in-app + email
      Title    : "Your Onboarding Training is Ready"
      Body     : "You have been enrolled in {N} onboarding courses. Please
                  complete them by {due_date}. Visit the Training section
                  to get started."

  - HR Admin:
      Channel  : in-app
      Title    : "Training Enrollment Confirmed"
      Body     : "{full_name} has been auto-enrolled in {N} mandatory
                  onboarding courses (due {due_date})."

INTEGRATION 6
Source App   : Onboarding
Target App   : Communications
--------------------------------------------------------------------------------
Trigger Event:
  Onboarding "Enable Access" action completes successfully (both
  User Management account creation and IT ticket submission have resolved
  without error). This fires asynchronously after Integration 3 and 4
  are acknowledged.

Action Taken in Target:
  A new post is created in the Communications app under the
  "All Employees" channel with type = announcement and priority = Low.
  The post is published immediately (published_at = now()).
  Content: "Please welcome {full_name} to the {department_name} team as
  {designation}! {full_name} joins us on {joining_date} — do give them a
  warm welcome."

Data Passed:
  - author_id            : system (HR system account)
  - audience_type        : 'all'
  - channel_id           : all_employees_channel_id (system constant)
  - post_type            : 'announcement'
  - priority             : 'low'
  - title                : "Welcome {full_name}!"
  - body                 : welcome message (template above)
  - published_at         : now()
  - reference_type       : 'onboarding'
  - reference_id         : onboarding_record.id

Sync Type    : Automatic (fires after Enable Access completes)

User Notification:
  - All Employees:
      Channel  : in-app (dashboard Announcements strip)
      Title    : "Welcome Announcement"
      Body     : "Please welcome {full_name} to the {department_name} team!"
      Note     : Low priority — no email, no web push. Dashboard strip only.

INTEGRATION 7
Source App   : Employee Directory
Target App   : User Management
--------------------------------------------------------------------------------
Trigger Event:
  An employee's status field in the employees table is set to Inactive or
  Exit. This can be triggered by:
    a) HR Admin manually setting status on the employee profile, OR
    b) Offboarding record reaching Completed status (see Integration 21).

Action Taken in Target:
  1. The corresponding app_users row is found by matching employees.work_email
     to app_users.email.
  2. app_users.status is set to 'inactive'.
  3. All active Supabase Auth sessions for the user are terminated via
     supabase.auth.admin.signOut(user_id, { scope: 'global' }).
  4. deactivated_at is stamped on both app_users and the employee record.
  5. An audit log entry is created in user_audit_log.

Data Passed:
  - user_id              : app_users.id (resolved by email match)
  - employee_id          : employees.id
  - deactivated_at       : now()
  - deactivation_reason  : 'employee_exit' | 'manual_deactivation' | 'offboarding'
  - deactivated_by       : acting_user_id (HR Admin who made the change)

Sync Type    : Automatic (AFTER UPDATE trigger on employees WHERE
               NEW.status IN ('inactive','exit'))

User Notification:
  - IT Admin (role = it_admin):
      Channel  : in-app + email
      Title    : "Employee Account Suspended — Action Required"
      Body     : "{full_name}'s system account has been suspended.
                  Please revoke physical access (ID badge, building access)
                  at the earliest."

  - HR Admin:
      Channel  : in-app
      Title    : "User Account Suspended"
      Body     : "{full_name}'s user account has been suspended and all
                  active sessions have been terminated."

INTEGRATION 8
Source App   : Employee Directory
Target App   : Collaboration
--------------------------------------------------------------------------------
Trigger Event:
  A new employee record is successfully created in the employees table
  (INSERT event). This fires after Integration 2 (Onboarding → Employee
  Directory) completes.

Action Taken in Target:

Data Passed:

  - employee_id          : employees.id
  - channel_ids[]        : [general_channel_id, department_channel_id (if exists)]
  - joined_at            : now()
  - added_by             : system

Sync Type    : Automatic (AFTER INSERT trigger on employees)

User Notification:
  - Employee:
      Channel  : in-app
      Title    : "You've Been Added to Channels"
      Body     : "You have been added to {N} channels: General
                  {and {department_name} if applicable}. Head to
                  Collaboration to say hello!"

  - Channel Admins (role = channel_admin for each affected channel):
      Channel  : in-app
      Title    : "New Member Added"
      Body     : "{full_name} has been added to #{channel_name}."

INTEGRATION 9
Source App   : Performance
Target App   : Training
--------------------------------------------------------------------------------
Trigger Event:
  A performance review is submitted (status transitions to
  'submitted' or 'completed') and at least one of the following is true:
    a) The skill_gap_notes field on the review is non-empty (length > 0), OR
    b) One or more competency ratings in competency_scores JSONB have a
       score value ≤ 2 (out of 5).

Action Taken in Target:
  1. The system reads the low-rated competency categories from the review.
  2. Queries the training_courses catalogue for courses where
     competency_tags overlap with the identified low-rated categories.
  3. Creates recommended_training records linking the employee to the
     matched course IDs (status = 'recommended', not yet enrolled).
  4. If manager_approval_required = false on the course (self-paced,
     low-cost courses), auto-enrollment can be triggered immediately.
  5. For courses requiring manager approval, a Workflow instance is created
     (see Workflow integration below).

Data Passed:
  - employee_id          → recommended_training.employee_id
  - review_id            → recommended_training.source_review_id
  - skill_categories[]   : competency names with score ≤ 2
  - recommended_course_ids[]: matched course IDs from catalogue
  - gap_notes            : skill_gap_notes (text, for context)
  - cycle_id             : performance_cycles.id

Sync Type    :
  Automatic  — Recommendation record creation (fires on review submit)
  Workflow   — Actual enrollment in manager-approval courses routes through
               a training_enrollment_approval workflow instance.

User Notification:
  - Employee:
      Channel  : in-app + email
      Title    : "Training Recommendations Based on Your Review"
      Body     : "Based on your {cycle_name} performance review, {N} training
                  courses have been recommended for you. Visit Training to
                  explore them."

  - Reporting Manager:
      Channel  : in-app
      Title    : "Skill Gap Identified — Training Recommended"
      Body     : "A skill gap was noted in {full_name}'s review
                  ({competency_names}). Training courses have been
                  recommended. Your approval may be required for enrollment."

INTEGRATION 10
Source App   : Performance
Target App   : Employee Directory
--------------------------------------------------------------------------------
Trigger Event:
  A performance review cycle is finalized — the HR Admin or Cycle Owner
  clicks "Finalize Cycle" on the cycle management page. The cycle status
  transitions to 'finalized' and calibrated ratings are locked.

Action Taken in Target:
  For every employee participating in the cycle, the following fields are
  written/updated on their employees table record:
    - latest_performance_rating is overwritten with final_rating
    - latest_review_cycle_id is set to the current cycle_id
    - An employee_performance_history row is inserted to preserve historical
      records (non-destructive append).

Data Passed (per employee):
  - employee_id          → employees.id
  - final_rating         → employees.latest_performance_rating
  - calibrated_rating    → employee_performance_history.calibrated_rating
  - competency_scores    → employee_performance_history.competency_scores (JSONB)
  - cycle_id             → employee_performance_history.cycle_id
                         + employees.latest_review_cycle_id
  - review_date          → employee_performance_history.finalized_at

Sync Type    : Automatic (fires on AFTER UPDATE on performance_cycles WHERE
               NEW.status = 'finalized'; processes all cycle participants
               in batch via Edge Function)

User Notification:
  - Each participating Employee:
      Channel  : in-app + email
      Title    : "Your {cycle_name} Review is Complete"
      Body     : "Your {cycle_name} performance review has been finalized.
                  Your overall rating: {rating_label}. You can view your
                  review letter in the Performance section."

INTEGRATION 11
Source App   : Performance
Target App   : Communications
--------------------------------------------------------------------------------
Trigger Event:
  A continuous feedback record of type = 'recognition' is submitted AND the
  is_public flag is set to true on the feedback record, AND the receiver has
  not opted out of public recognition (employees.recognition_opt_out = false).

Action Taken in Target:
  1. A new record is inserted into communications_recognitions.
  2. A new communications_posts record is created with:
       post_type = 'recognition'
       channel   = 'general' (all-employees) or recognition-specific channel
       body      = recognition message + badge display
       published_at = now()
  3. The badge_type and message from the feedback record are rendered into
     the post template.

Data Passed:
  - giver_id             : feedback.submitted_by (employee_id)
  - receiver_id          : feedback.subject_employee_id
  - badge_type           : feedback.badge_type (e.g., 'Innovator', 'Team Player')
  - message              : feedback.feedback_text
  - recognition_id       : feedback.id (cross-reference)
  - post_type            : 'recognition'
  - audience_type        : 'all'
  - priority             : 'low'

Sync Type    : Automatic (fires on INSERT into continuous_feedback WHERE
               NEW.type = 'recognition' AND NEW.is_public = true)

User Notification:
  - Recognition Receiver:
      Channel  : in-app + web push
      Title    : "You Received a Recognition!"
      Body     : "{giver_name} recognized you with a {badge_type} badge:
                  '{message_preview}'"

  - All Employees (Communications feed followers):
      Channel  : in-app (feed item in Communications)
      Note     : No push — visible as a feed post only unless they
                  explicitly follow the recognition channel.

INTEGRATION 12
Source App   : Performance
Target App   : Workflow Automation
--------------------------------------------------------------------------------
Trigger Event:
  A Performance Improvement Plan (PIP) record is created (INSERT into
  performance_pips table). This can be initiated by a Manager or HR
  from the employee's review page.

Action Taken in Target:
  1. A new workflow_instances row is created using the pre-defined
     pip_creation_approval workflow template.
  2. The first step (HR Manager approval) is assigned to the HR Manager
     role for the relevant department.
  3. The PIP record status is set to 'pending_approval' — the employee
     is NOT notified at this stage.
  4. Only after HR Manager approves does the PIP status transition to
     'active' and the employee notification fires.

Data Passed:
  - pip_id               → workflow_instances.entity_id
  - employee_id          → workflow context variable
  - created_by           → workflow context variable (initiating manager/HR)
  - pip_details          → workflow context: start_date, end_date, goals[],
                           review_frequency, escalation_contacts[]
  - department_id        → used to resolve HR Manager approver

Sync Type    : Workflow (routed through Workflow Automation)

User Notification:
  - HR Manager (approval step assignee):
      Channel  : in-app + email + web push
      Title    : "Approval Required: PIP for {full_name}"
      Body     : "A Performance Improvement Plan has been initiated for
                  {full_name} by {initiator_name}. Your approval is required
                  before the employee is informed."

  - Employee (ONLY after HR Manager approves):
      Channel  : in-app + email
      Title    : "Performance Improvement Plan"
      Body     : "A Performance Improvement Plan has been created for you.
                  Please review the details and schedule a meeting with
                  your manager."

  - Initiating Manager (on approval or rejection):
      Channel  : in-app
      Title    : "PIP {Approved / Rejected}"
      Body     : "The PIP for {full_name} has been {approved / rejected}
                  by {hr_manager_name}. {Rejection reason if applicable.}"

Trigger Event:

INTEGRATION 16
Source App   : Recruitment
Target App   : Workflow Automation
--------------------------------------------------------------------------------
Trigger Event:
  A new Job Requisition is submitted by a Department Manager or HR
  (INSERT into job_requisitions with status = 'submitted').

Action Taken in Target:
  1. A workflow_instances row is created for the job_requisition_approval
     workflow template.
  2. Step 1 — Department Manager approval (assigned to the department head
     for the requisition's department).
  3. Step 2 — HR Manager final approval (assigned after Step 1 completes).
  4. On full approval: job_requisitions.status = 'approved', a job_postings
     record is created and activated.
  5. On rejection at any step: job_requisitions.status = 'rejected',
     rejection_reason recorded, requester notified.

Data Passed:
  - req_id               → workflow_instances.entity_id
  - position             → workflow context: position_title
  - department_id        → workflow context (used to resolve approvers)
  - headcount            → workflow context
  - justification        → workflow context (text)
  - requested_by         → workflow context (employee_id of requester)
  - priority             → workflow context (urgent | normal | backfill)

Sync Type    : Workflow

User Notification:
  - Department Manager (Step 1 approver):
      Channel  : in-app + email + web push

INTEGRATION 18
Source App   : All Apps
Target App   : Notification Bell (Global)
--------------------------------------------------------------------------------
Rule:
  Every app in the HR Portal that generates a user-facing event MUST create
  a notification record by calling the centralized notification write path.
  This is the single source of truth for all bell notifications.

Write Path:
  Option A (recommended): Direct INSERT into notifications table with RLS
  policies enforcing that only service_role or the appropriate app service
  account can write.

  Option B: POST to /api/notifications (if routing through an API layer).
  The API layer validates and inserts into the notifications table.

Required fields for every notification:
  - user_id              : UUID of the recipient (from auth.users)
  - title                : Short notification title (max 80 chars)
  - body                 : Notification body text (max 300 chars)
  - type                 : Enum:
                             action_required | info | warning |
                             success | error
  - app_filter           : Enum: dashboard | directory | recruitment |
                             onboarding | user_management | performance |
                             training | communications | collaboration |
                             workflow
  - entity_type          : String identifying the record type
                           (e.g., 'leave_request', 'review_cycle')
  - entity_id            : UUID of the specific record
  - deep_link            : Relative URL for navigation
                           (e.g., /performance/reviews/{id})
  - is_read              : boolean, default false
  - created_at           : timestamptz, default now()
  - expires_at           : optional; notifications older than this are
                           auto-archived

Real-Time Delivery:
  The Notification Bell UI component subscribes to the notifications table
  via Supabase Realtime:
    supabase
      .channel('user-notifications')
      .on('postgres_changes', {
          event: 'INSERT',
          schema: 'public',
          table: 'notifications',
          filter: 'user_id=eq.{current_user_id}'
        }, handleNewNotification)
      .subscribe()

  This ensures zero-polling real-time delivery via websocket for all apps.

Web Push Delivery:
  In addition to the Realtime bell, any notification with
  send_web_push = true triggers the Web Push service (Supabase Edge
  Function push_dispatcher) which uses the VAPID keys and stored
  push_subscriptions for the user.

Notes on Web Push:
  1. Web push requires browser opt-in via the service worker permission
     prompt. Users who have not opted in receive in-app + email fallback.
  2. Web Push = N does not mean the event is silent — it means it uses
     in-app bell only (or email in some cases). Review each entry for
     the full channel specification.
  3. All Action-Required type events should be treated as candidates for
     web push upgrade if conversion data shows them being missed.
  4. The push_dispatcher Edge Function routes all web push events and
     reads per-user push_subscriptions from the database. It should
     batch per-user when multiple events fire in quick succession
     (< 5 seconds) to avoid push spam.
