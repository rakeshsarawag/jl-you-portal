    - "All Departments" = omit the filter param (not send empty string).
    - Department Manager role: force-filter to their own dept (see Validation Rules).

SECTION 2 — FEATURE ENHANCEMENTS
--------------------------------------------------------------------------------

2.1 Data Pipeline — Proper Backend Aggregation
  - All KPI calculations move to server; zero client-side aggregation.
  - New Supabase Edge Functions:
      GET /analytics/summary?from={}&to={}&department={}
        Returns: JSON object with all 12 KPI values computed via DB aggregation
        (SUM, COUNT, AVG queries across relevant tables).
  - Caching Strategy:
      Cache key: `analytics_summary_{from}_{to}_{department}`
      TTL: 15 minutes per unique filter combination.
      Implementation: Supabase edge function uses in-memory cache or Redis (if
      available); alternatively cache in analytics_cache table with expires_at.
  - Stale Indicator:
      Each KPI card shows: "Data as of {relative_time}" e.g. "Data as of 2 min ago"
      Timestamp sourced from server response header or response body `computed_at`.
      Color: gray-400, font-size: 11px, positioned below value.
  - Manual Refresh: [Refresh] button in control bar invalidates cache and re-fetches.

      by_department: [{ dept, count, delta_percent }]

2.4 Anomaly Detection (New Feature)

  Detection Rules (run on each /analytics/summary refresh):
    Rule A — Headcount spike/drop:
      Condition: |current_headcount - prev_period_headcount| / prev > 0.10
      Severity: amber if 10-20%, red if >20%
    Rule B — Invoice overdue spike:
      Condition: overdue_invoice_count > (prev_period_overdue * 1.25)
      Severity: amber
    Rule C — IT SLA breach rate:
      Condition: sla_breach_rate > 0.20  (20%)
      Severity: red
    Rule D — Training compliance drop:
      Condition: training_completion_pct < (prev_period_completion - 0.15)
      Severity: amber

  Anomaly Indicators on KPI Cards:
    Amber dot: top-right corner of card when anomaly detected (amber severity)
    Red dot + amber-50 card background + amber border: red severity
    Hover tooltip on dot: "{metric} is {deviation}% above/below normal"

  Anomaly History Log:
    Shown in Overview tab below KPI grid as collapsible panel: "Recent Anomalies"
    Table: Date | Metric | Deviation % | Severity chip | Resolved Y/N
    [Mark Resolved] button per row
    Persisted in analytics_anomalies table (see Data Model)

  Anomaly Notification:
    On detection: POST to notifications service → push notification to admin
    (see Push Notifications section)

2.5 Comparison Mode (New Feature)

  Toggle: [Compare Period] toggle in control bar (default: off)
  When enabled:
    Fetch two datasets: current period + equivalent previous period (same duration)
    Example: "Last 30 days" current + "30 days prior" as previous
    API: same /analytics/summary endpoint called twice with different date ranges

  KPI Cards in Compare Mode:
    Show: current value + previous value (smaller, gray)
    Delta chip: shows change from previous to current

  Charts in Compare Mode:
    Line/bar charts render two series:
      "Current Period" — indigo (#6366F1), solid line
      "Previous Period" — gray (#9CA3AF), dashed line
    Legend below each chart

  Delta Summary Row (below KPI grid):
    Row of pills: one per KPI
    Green pill: metric improved (↑ +N%)
    Red pill: metric declined (↓ -N%)
    Gray pill: no significant change (<1%)

SECTION 3 — DATA MODEL
--------------------------------------------------------------------------------

Table: analytics_saved_reports
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid()
  name            TEXT NOT NULL
  created_by      UUID NOT NULL REFERENCES auth.users(id)
  domain          TEXT[] NOT NULL                    -- selected domain tabs
  metric_config   JSONB NOT NULL DEFAULT '{}'        -- metric selections per domain
  filter_config   JSONB NOT NULL DEFAULT '{}'        -- { department, status, etc. }
  date_from       DATE
  date_to         DATE
  schedule        TEXT CHECK (schedule IN (
                    'one_off','daily','weekly',
                    'monday_morning','first_of_month'))
  recipients      TEXT[] DEFAULT '{}'               -- email addresses
  last_run_at     TIMESTAMPTZ
  next_run_at     TIMESTAMPTZ
  is_active       BOOLEAN NOT NULL DEFAULT TRUE
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
  UNIQUE (name, created_by)

Table: analytics_report_runs
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid()
  report_id       UUID NOT NULL REFERENCES analytics_saved_reports(id) ON DELETE CASCADE
  run_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()
  triggered_by    TEXT NOT NULL CHECK (triggered_by IN ('schedule','manual'))
  status          TEXT NOT NULL CHECK (status IN ('running','completed','failed'))
  output_url      TEXT                              -- Supabase Storage URL of output file
  row_count       INTEGER
  error           TEXT
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()

Table: analytics_anomalies
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid()
  metric_key       TEXT NOT NULL               -- e.g. 'headcount', 'sla_breach_rate'
  detected_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
  current_value    NUMERIC NOT NULL
  baseline_value   NUMERIC NOT NULL
  deviation_percent NUMERIC NOT NULL           -- signed: positive = above, negative = below
  severity         TEXT NOT NULL CHECK (severity IN ('amber','red'))
  resolved_at      TIMESTAMPTZ
  acknowledged_by  UUID REFERENCES auth.users(id)
  filter_snapshot  JSONB                       -- { department, from, to } at detection time
  created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()

Table: analytics_cache (optional — if not using in-memory cache)
  cache_key        TEXT PRIMARY KEY            -- hash of filter params
  data             JSONB NOT NULL
  computed_at      TIMESTAMPTZ NOT NULL
  expires_at       TIMESTAMPTZ NOT NULL
  INDEX ON expires_at

SECTION 5 — VALIDATION RULES
--------------------------------------------------------------------------------

VR-A1: Date range — from must be before to (from < to).
VR-A2: Date range — max span 365 days for standard users; unlimited for admin role.
VR-A3: Custom date range — both from and to required when preset = 'custom'.
VR-A4: Saved report name — required; unique per user (enforced by DB UNIQUE constraint).
VR-A5: Saved report name — max 100 characters.
VR-A6: Schedule — if schedule is 'daily', 'weekly', 'monday_morning', or 'first_of_month':
         at least 1 recipient email required; max 10 recipients.
VR-A7: Schedule recipient emails — validate email format on input.
VR-A8: Custom report builder — must select at least 1 domain before proceeding to Step 2.
VR-A9: Custom report builder — must select at least 1 metric before generating preview.
VR-A10: Department filter access — if authenticated user's role = 'department_manager':
          force-apply department = their own department; department dropdown is hidden/
          read-only showing only their department. Cannot access cross-department data.
VR-A11: Anomaly acknowledgment — only admin or analytics_admin role may mark resolved.
VR-A12: Report deletion — only report creator or admin may delete a saved report.

SECTION 6 — CROSS-APP INTEGRATIONS
--------------------------------------------------------------------------------

Analytics reads aggregated data from:
  Employee Directory   → headcount, dept breakdown, employment types
  Recruitment          → pipeline stages, time-to-hire, active candidates
  Onboarding           → onboarding completion rates
  Performance          → review scores, performance distribution
  Training             → course enrollment, completion rates, satisfaction
  Payroll              → total payroll, payroll by dept, month-over-month
  Invoices             → revenue, overdue amounts, client breakdown
  IT Services          → ticket volume, SLA compliance, categories
  Assets               → utilization, depreciation totals
  Projects             → on-track count, milestone completion
  OKR                  → objective progress, key result attainment
  Collaboration        → engagement metrics (message volume, active users)

Analytics → Executive Dashboard:
  Executive Dashboard calls same /analytics/summary endpoint.
  Shared cache layer — exec dashboard benefits from analytics warm cache.
  No duplicate aggregation logic.

Analytics → Notifications Bell:
  When anomaly detected: call notification service to create in-app notification
  and send web push to admin and analytics_admin roles.
  Notification payload: { type:'anomaly_detected', metric_key, deviation_percent }

Scheduled Reports → Communications Hub:
  Optional: when saving a report, checkbox "Post summary to Communications Hub"
  On completion: call Communications Hub API to create announcement with report summary
  Announcement body: generated HTML table of top metrics + link to full report.

Analytics → Workflow Automation:
  Anomaly detection → trigger workflow:
    Rule: if metric_key='sla_breach_rate' AND severity='red' → trigger
    escalation_workflow template.
  Implementation: on anomaly insert, call Workflow Automation trigger endpoint:
    POST /workflows/trigger { trigger:'anomaly_detected', metadata:{ metric_key, severity } }
  Configurable in Workflow Automation app: admin maps anomaly events to workflow templates.

SECTION 7 — PUSH NOTIFICATIONS
--------------------------------------------------------------------------------

Event: anomaly_detected
  Trigger: analytics_anomalies row inserted with severity = 'red' or 'amber'
  Recipients: admin, analytics_admin roles
  Priority: warning
  Title: "Analytics Anomaly Detected"
  Body: "{metric_name} anomaly detected: {deviation}% above/below normal"
  Action URL: /analytics?tab=overview&highlight={metric_key}

Event: scheduled_report_ready
  Trigger: analytics_report_runs row updated to status = 'completed'
  Recipients: report.recipients list (email + push if they have web push enabled)
  Priority: info
  Title: "Analytics Report Ready"
  Body: '"{report_name}" is ready — view in Analytics'
  Action URL: /analytics?tab=reports&run={run_id}

Event: report_run_failed
  Trigger: analytics_report_runs row updated to status = 'failed'
  Recipients: report creator only
  Priority: warning
  Title: "Scheduled Report Failed"
  Body: 'Scheduled report "{report_name}" failed to run. Check configuration.'
  Action URL: /analytics?tab=reports&report={report_id}

Event: kpi_threshold_breached
  Trigger: /analytics/summary response value outside alert_threshold_low/high from KPI catalog
  Recipients: admin role
  Priority: warning
  Title: "KPI Threshold Breached"
  Body: "{metric_name} exceeded threshold: {current_value} vs threshold {threshold_value}"
  Action URL: /analytics?tab=overview

SECTION 4 — VALIDATION RULES
--------------------------------------------------------------------------------

VR-S1: Audit logs — append-only. RLS policies: ALLOW INSERT for authenticated;
         DENY UPDATE and DELETE for all roles including service_role
         (use a separate archive process, not delete).
VR-S2: Audit log retention — configurable in Master Data: key='AUDIT_LOG_RETENTION_DAYS'
         default=90. Archive job moves old rows to audit_logs_archive; never deletes.
VR-S3: Compliance requirement status change — requires:
         (a) status_change_reason text, minimum 20 characters
         (b) For status='compliant': at least 1 evidence attachment required
         Validated in API before UPDATE; returns 422 if not met.
VR-S4: Privacy request due_date — auto-calculated server-side; cannot be shortened
         below regulation minimum (30d GDPR, 45d CCPA). API rejects manual
         due_date values that are earlier than regulation minimum from received_at.
VR-S5: Security risk score — computed column (likelihood × impact); never set manually.
         Both likelihood and impact must be 1, 2, or 3 (DB CHECK constraint).
VR-S6: Evidence file constraints:
         Max file size: 20 MB (validated client-side and in Supabase Storage policy)
         Allowed MIME types: application/pdf, image/*, application/msword,
           application/vnd.openxmlformats-officedocument.wordprocessingml.document,
           application/vnd.ms-excel,
           application/vnd.openxmlformats-officedocument.spreadsheetml.sheet,
           text/csv
VR-S7: Privacy request completion — response_notes required (min 20 chars) before
         status can be set to 'completed' or 'rejected'.
VR-S8: Compliance assessment score — 0–100 range enforced by DB CHECK constraint
         and API validation.
VR-S9: Risk review aging — risks with last_reviewed_at < (TODAY - 90 days) are
         flagged in UI with amber indicator; push notification sent to risk owner.

  password_reset events auto-logged (see Step 3 event list above).
  Login failure spike detection: Security app queries audit_logs for
    COUNT(event_type='login_failure') WHERE user_email={email} AND timestamp > NOW()-1h
    If count >= 5: trigger login_failure_spike notification.

SECTION 6 — PUSH NOTIFICATIONS

Event: critical_audit_event
  Trigger: audit_logs INSERT with severity = 'critical'
  Recipients: all users with role IN ('admin', 'security')
  Priority: immediate (high)
  Title: "Critical Security Event"
  Body: "Critical security event: {action} by {user_email}"
  Action URL: /security?tab=audit-logs&highlight={event_id}
  Web push: YES (immediate); in-app bell: YES

Event: login_failure_spike
  Trigger: >5 login_failure events for same email within 1-hour window
  Recipients: admin role
  Priority: warning
  Title: "Multiple Failed Logins Detected"
  Body: "Multiple failed logins detected for {user_email}: {N} attempts in 1 hour"
  Action URL: /security?tab=audit-logs&filter=login_failure&user={email}

Event: compliance_deadline_7d
  Trigger: compliance_assessments with next due date = TODAY + 7 days (daily cron check)
  Recipients: framework assigned_to user + admin
  Priority: warning
  Title: "Compliance Assessment Due Soon"
  Body: "{framework_name} assessment is due in 7 days"
  Action URL: /security?tab=compliance&framework={framework_id}

Event: privacy_request_overdue
  Trigger: daily cron: privacy_requests WHERE due_date < TODAY AND status NOT IN ('completed','rejected')
  Recipients: assigned_to user + admin
  Priority: action_required
  Title: "Privacy Request Overdue"
  Body: "Privacy request from {requester_name} is {N} days overdue"
  Action URL: /security?tab=privacy-requests&highlight={request_id}

Event: data_export_by_admin
  Trigger: audit_logs INSERT with event_type = 'data_export' AND user_role = 'admin'
  Recipients: other admin users (all admin role, excluding the exporting user)
  Priority: info
  Title: "Admin Data Export"
  Body: "{user_email} exported {resource_type} data at {timestamp}"
  Action URL: /security?tab=audit-logs&highlight={event_id}

Event: security_risk_review_due
  Trigger: daily cron: security_risks WHERE last_reviewed_at < TODAY - 90 days AND status NOT IN ('resolved','accepted')
  Recipients: risk owner (owner field)
  Priority: warning
  Title: "Security Risk Review Due"
  Body: "Security risk '{title}' has not been reviewed in 90+ days"
  Action URL: /security?tab=risk-register&highlight={risk_id}

Event: compliance_status_degraded
  Trigger: after compliance_requirements UPDATE: recalculate compliance_pct; if
    new_pct < previous_pct - 5 (i.e. dropped more than 5 percentage points)
  Recipients: admin role
  Priority: warning
  Title: "Compliance Score Dropped"
  Body: "{framework_name} compliance dropped to {score_percent}%"
  Action URL: /security?tab=compliance&framework={framework_id}
