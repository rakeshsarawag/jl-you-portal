G1 — MFA / 2FA Configuration Panel (Priority: Medium)
  Problem  : No multi-factor authentication management for admins or users.
  Solution : Add a dedicated "MFA" section within the user detail slide-over and
             a global MFA policy panel in Settings.
  Implementation:
    - Call supabase.auth.mfa.enroll() to generate a TOTP secret and QR code URI.
    - Render QR code on-screen using a lightweight library (e.g., qrcode.react).
    - Generate and display 10 single-use backup codes; allow admin to regenerate.
    - Per-role "Enforce MFA" toggle stored in Permissions App role config.
    - On next login, if MFA is enforced for the user's role and mfa_enrolled = false,
      redirect user to mandatory enrollment screen before dashboard access is granted.
    - Admin can reset MFA for a user (wipes mfa_enrolled = false, clears factors
      via supabase.auth.admin.mfa.deleteFactor(userId, factorId)).

G2 — Audit Log CSV Export (Priority: Low)
  Problem  : Audit log has no export capability.
  Solution : Add "Export CSV" button in the Audit Log tab toolbar.
  Implementation:
    - Apply current active filters (user, date range, action type) to the query.
    - Fetch all matching rows (not paginated) up to a configurable limit (default 10,000).
    - Convert to CSV client-side using papaparse or a simple manual serialiser.
    - Trigger browser download with filename: audit_log_YYYY-MM-DD.csv
    - Columns exported: timestamp, user_name, user_email, action, entity_type,
      entity_id, old_value, new_value, reason, ip_address, session_id.

G3 — Deactivate vs Delete UX (Priority: Medium)
  Problem  : The two actions look and behave identically, causing admin confusion.
  Solution : Visually and functionally distinguish Deactivate and Delete everywhere.
  Implementation:
    Deactivate:
      - Sets app_users.status = 'inactive'; does NOT touch Supabase Auth user.
      - User cannot log in (app-level guard checks status on every authenticated request).
      - Data fully retained; user remains visible in admin list with "Inactive" badge.
      - Row visually dimmed (opacity-50, gray text, gray badge).
      - Reversible via [Reactivate] action.
    Delete (Soft):
      - Sets app_users.status = 'deleted', app_users.deleted_at = NOW().
      - Hidden from all non-admin views; admin filter "Show Deleted" reveals them.
      - Data retained for 90 days, then purged by a scheduled Supabase Edge Function
        (cron: 0 2 * * * — runs daily at 02:00 UTC).
      - Supabase Auth account is also disabled at delete time.
      - Send admin warning notification 7 days before permanent purge.
    Confirmation dialogs:
      - Deactivate dialog: "Deactivate {name}? They will lose access but their data
        is retained. You can reactivate them at any time." [Cancel] [Deactivate]
      - Delete dialog: two-step — step 1 shows a warning summary; step 2 requires
        admin to type the user's email address to confirm. Clearly states:
        "This will be permanently purged in 90 days."

G4 — Session Management / Force Logout (Priority: Medium)
  Problem  : No visibility into active sessions; cannot terminate a session remotely.
  Solution : Add "Sessions" tab; implement force-logout capability.
  Implementation:
    - Query active sessions from Supabase Auth via
      supabase.auth.admin.listUserSessions(userId) per user, or aggregate across all
      users for the global sessions view.
    - [Force Logout] calls supabase.auth.admin.signOut(userId, { scope: 'global' })
      to invalidate all refresh tokens for that user.
    - Single-session force logout: invalidate specific session by session_id if
      Supabase Admin API supports per-session revocation; otherwise force global
      logout and notify user.
    - Force logout requires admin confirmation dialog with mandatory reason field;
      action is written to audit_logs with reason, admin id, session_id.

G5 — Last Login Column (Priority: Low)

G7 — Invitation by Email Flow (Priority: Medium)
  Problem  : New users can only be created by admin entering all details manually.
  Solution : Add [Invite User] button with guided invite flow.

        app_users.invitation_sent_at = NOW()

D5.2.1  User Lifecycle Management
---------------------------------------
User States (ordered lifecycle):
  1. Pending   — Invited but setup not yet completed.
                 Supabase Auth account exists; app_users.status = 'pending'.
  2. Active    — Normal operational state; full access per assigned role.
                 app_users.status = 'active'.
  3. Inactive  — Deactivated by admin; login blocked at app-layer guard.
                 app_users.status = 'inactive'.
                 Reversible → Active.
  4. Deleted   — Soft-deleted; hidden from standard views; data retained 90 days.
                 app_users.status = 'deleted', deleted_at populated.
                 Irreversible (no reactivation after soft delete).

Visual State Indicators (user list rows):
  - Active  : Normal row; green "Active" badge (bg-green-100 text-green-700).
  - Pending : Blue "Awaiting Setup" badge (bg-blue-100 text-blue-700).
  - Inactive: Row dimmed (opacity-50); gray "Inactive" badge; italic text.
  - Deleted : Only shown when admin enables "Show Deleted" filter; red-tinted row;
              red "Deleted" badge; deletion date shown.

Bulk State Actions (multi-select toolbar, appears when ≥1 row selected):
  [Deactivate]           — Sets selected Active users to Inactive.
  [Reactivate]           — Sets selected Inactive users to Active.
  [Force Password Reset] — Triggers supabase.auth.admin.generateLink({ type: 'recovery' })
                           for each selected user; sends password reset email.
  [Assign Role]          — Opens role assignment modal; applies same role to all
                           selected users; requires reason; logs in audit.
  Validation: bulk actions skip any user for which the action is not valid (e.g.,
  cannot deactivate a Deleted user); summary toast shows X succeeded, Y skipped.


D5.2.2  Role Management Integration with Permissions App
----------------------------------------------------------
  - Roles are NOT hardcoded in User Management; they are read from the Permissions
    App via internal API: GET /api/permissions/roles?include=description,permissions
  - Role selector in user forms shows: Role Name | Brief description |
    Permission summary chip list (e.g. "Can view payroll", "Can approve leave").
  - Role assignment UI includes a permission diff preview when changing an existing
    role: "Gaining: [list] | Losing: [list]".
  - Role change flow:
      1. Admin selects new role from dropdown (permission diff shown).
      2. Reason field (required, min 10 characters).
      3. [Confirm Change] button.
      4. On confirm: app_users.role updated; audit_log entry created with:
           action        : 'role_change'
           old_value     : { role: previousRole }
           new_value     : { role: newRole }
           reason        : admin-entered reason
           changed_by    : admin user id
           timestamp     : NOW()
  - Role hierarchy enforcement: an admin cannot assign a role with a higher permission
    level than their own role level (see Validation Rules, D5.4).


D5.2.3  Session Management Tab
---------------------------------------
  Location: "Sessions" tab in User Management (new tab, 4th position).

  Table Columns:
    User        — Avatar + name + email link to user detail.
    Device      — Chip: "Desktop Chrome" / "Mobile Safari" / "Tablet Firefox"
                  (parsed from user_agent).
    IP Address  — Displayed; click to copy.
    Location    — Geo-resolved city/country from IP (via ip-api.com or similar,
                  server-side to avoid CORS).
    Session Start — Relative + absolute timestamp.
    Last Active   — Relative timestamp; green dot if < 5 min ago.
    Actions       — [Force Logout] red ghost button (text-red-600 border-red-300).

  Filters:
    - Toggle: "Active sessions only" (default on).
    - User search/filter dropdown.
    - Date range filter on Session Start.

  Suspicious Login Detection:
    - A session is flagged "Suspicious" when:
        a) New device fingerprint for that user (no prior session from same
           user_agent + device_type combination).
        b) New country/region compared to last 10 sessions.
        c) Login within 1 hour from a geographically impossible second location
           (velocity check: distance / time > ~1000 km/h).
    - Suspicious sessions show a red "⚠ Suspicious" chip in the Device column.
    - Admin receives in-app warning notification; event written to audit_log with
      action: 'suspicious_login'.
    - User also receives a "New device login" warning push notification.


D5.2.4  MFA Configuration Panel
---------------------------------------
  Accessible from: user detail slide-over → "Security" section; also from a global
  MFA Policy panel in Settings → Security.

  Per-User MFA Statuses:
    - Not Enrolled  : mfa_enrolled = false; no factors registered.
    - Enrolled      : mfa_enrolled = true; at least one active TOTP factor.
    - Enforced      : mfa_enrolled = true AND user's role has enforce_mfa = true.

  Admin Actions:
    Enforce MFA for a Role:
      - Toggle in Permissions App role config: enforce_mfa (boolean).
      - When enabled, all users with that role and mfa_enrolled = false are
        intercepted at login with a mandatory enrollment screen.
      - Existing enrolled users are unaffected.
    Reset MFA for a User (e.g. lost device):
      - Admin clicks [Reset MFA] in user security panel.
      - System calls supabase.auth.admin.mfa.deleteAllFactors(userId).
      - Sets app_users.mfa_enrolled = false.
      - Sends "MFA Reset" info notification to the user.
      - Writes to audit_log: action: 'mfa_reset', changed_by: admin id.
    MFA Enrollment (user-initiated from My Profile):
      - Call supabase.auth.mfa.enroll({ factorType: 'totp' }).
      - Display returned QR code URI rendered as QR image.
      - Display 10 backup codes (generated server-side, stored hashed in Supabase
        Auth; shown only once — user must download/copy before proceeding).
      - User enters TOTP code from authenticator app to verify.
      - On success: supabase.auth.mfa.challengeAndVerify() → sets mfa_enrolled = true.


D5.2.5  Login History Tab
---------------------------------------
  Location: "Login History" tab in User Management (new, 5th position).
  Data source: login_history table (populated by Supabase Auth webhook on sign-in
  events + application-layer logging for failed attempts).

  Table Columns:
    User      — Avatar + name.
    Timestamp — Full date/time; relative in secondary text.
    IP        — With copy action.
    Location  — City, Country (geo-resolved).
    Device    — User agent summary chip.
    Status    — Badge: Success (green) | Failed (red) | Suspicious (amber).

  Filters:
    - Search by user name or email.
    - Date range picker (default: last 7 days).
    - Status filter: Success | Failed | Suspicious | All.

  Automated Alert — Brute Force Detection:
    - If ≥5 failed login attempts for the same account within any rolling 60-minute
      window, an alert is triggered:
        * In-app urgent notification to all admins.
        * Account automatically set to 'locked' (sub-state of Inactive) for 30 minutes.
        * audit_log entry: action: 'account_locked_brute_force'.
        * User receives email notification: "Your account has been temporarily locked
          due to multiple failed sign-in attempts."

D5.2.7  Invitation Flow
---------------------------------------
  Trigger: [Invite User] button (top-right of Users tab, secondary to [+ Create User]).

  Slide-over panel fields:
    - Email address (required; validated; must not already exist in app_users).
    - Role (required; dropdown from Permissions App; shows permission summary).
    - Department (optional; dropdown from Master Data App).
    - Personal note (optional; appended to invitation email body).

  On [Send Invitation]:
    1. supabase.auth.admin.generateLink({ type: 'invite', email: enteredEmail }).
    2. Insert row to app_users:
         email                  = enteredEmail
         role                   = selectedRole
         department_id          = selectedDepartment (nullable)
         status                 = 'pending'
         invitation_sent_at     = NOW()
         invitation_expires_at  = NOW() + interval '72 hours'
         invited_by             = currentAdminId
    3. Send in-app notification to invitee (info): "You've been invited to the HR Portal."
    4. audit_log entry: action: 'user_invited', entity_id: new user id.

  Pending user row actions:
    [Resend Invite]  — Only available when invitation_expires_at < NOW() OR within
                       72h window. Increments resend_count. Blocked when resend_count >= 3
                       (show tooltip: "Max resend attempts reached. Delete and recreate
                       the invitation.").
    [Cancel Invite]  — Sets status = 'deleted' (soft), marks invitation void.

  On invitation completion by user:
    - Supabase Auth webhook (event: USER_UPDATED, email_confirmed_at populated) fires.
    - Edge Function: update app_users.status = 'active', cleared invitation fields.
    - Attempt to match employee_directory record by email; if found, link
      app_users.employee_id = matched employee.id.
    - Send welcome info push notification to user.


D5.2.8  Access Review Tab
---------------------------------------
  Location: "Access Review" tab in User Management (new, last tab).
  Trigger: Quarterly schedule (cron: 0 9 1 1,4,7,10 * — 09:00 UTC on 1 Jan, Apr, Jul, Oct).
           Admin can also manually initiate a review cycle.

  Access Review Cycle record:
    - review_period  : e.g. "Q3 2026"
    - initiated_by   : admin user id
    - initiated_at   : timestamp
    - due_date       : initiated_at + 30 days
    - status         : In Progress | Completed

  Review table (one row per active/inactive user):
    Columns: User | Current Role | Department | Last Login | Days Since Review |
             Reviewer (HR/Admin assigned) | Action | Notes | Review Status

  Review Actions per user row:
    [Confirm Access]  — Role and access confirmed as appropriate.
    [Revoke Access]   — Deactivates user; reason required.
    [Change Role]     — Opens role change modal; reason required.

  Flagging Logic:
    - Users not reviewed for >90 days are flagged with an amber "Overdue Review" badge.
    - Users with status = 'inactive' for >180 days flagged with "Consider Deletion".

  Access Review Record stored in user_access_reviews:
    id           | reviewed_by (user_id) | review_date | user_id | action
    (confirmed / revoked / role_changed) | notes | cycle_id

  Export:
    - [Export PDF] button generates a formatted access review report:
        Cover page: review period, initiated by, completion date.
        Summary table: total users, confirmed, revoked, role changes.
        Detail table: full review log.
    - PDF generated server-side via a Supabase Edge Function using a headless
      HTML-to-PDF approach (e.g., Puppeteer or a PDF generation library).

D5.4  VALIDATION RULES
--------------------------------------------------------------------------------

V-UM-01  Cannot delete a user who has been active (last_sign_in_at or any audit
         event) within the last 30 days. The delete action is blocked with a
         message: "This user was active within the last 30 days. Deactivate them
         first, then delete after 30 days of inactivity."

V-UM-02  Role elevation guard: an admin cannot assign a role with a permission
         level higher than their own role's permission_level integer. Enforced
         server-side in the role assignment endpoint. Client hides ineligible roles
         from the dropdown but server rejects the request regardless.

V-UM-03  Self-deactivation guard: an admin cannot deactivate their own account.
         Enforced both client-side (hide action on own row) and server-side
         (403 Forbidden if user_id === requester_id in deactivate endpoint).

V-UM-04  Invitation link expiry: link expires 72 hours after invitation_sent_at.
         Maximum 3 resend attempts (resend_count <= 3); 4th attempt returns HTTP 409
         with message requiring manual recreation.

V-UM-05  Password requirements (configurable per org in Master Data App → Security Settings):
         Default: min 12 characters, at least 1 uppercase, 1 lowercase, 1 numeric,
         1 special character (!@#$%^&*()-_+=). Supabase password policy configured
         via Supabase Dashboard or Management API. Client-side zxcvbn strength meter
         displayed during password creation.

V-UM-06  MFA enforcement: if a user's role has enforce_mfa = true and mfa_enrolled
         = false, the user is redirected to MFA enrollment immediately after successful
         password authentication. Session is issued a restricted 'mfa_pending' scope
         that blocks all app routes except /mfa-enrollment. No bypass or "skip"
         option is presented.

V-UM-07  Force logout requires: admin must enter a reason (min 5 characters) in the
         confirmation dialog. Action logged in audit_logs with reason, target user id,
         admin id, session_id.

V-UM-08  Bulk actions: a single bulk action request is limited to 100 users at a time
         to prevent timeout. Client enforces selection cap and shows warning if user
         attempts to select more.

V-UM-09  Profile picture upload: max 5 MB, accepted MIME types image/jpeg, image/png,
         image/webp only. Client-side validation before upload; server-side Storage
         policy rejects non-conforming uploads.

V-UM-10  Access review: each user must have a review action recorded (confirmed /
         revoked / role_changed) before the cycle can be marked Completed. Cycle
         "Complete" button is disabled until 100% of users are reviewed; progress
         counter shown: "142 / 157 reviewed".

D5.5  CROSS-APP INTEGRATIONS
--------------------------------------------------------------------------------

INT-UM-01  Employee Directory → User Management
  Trigger  : Employee status set to 'terminated' or 'inactive' in Employee Directory.
  Action   : Automatically set linked app_users.status = 'inactive';
             terminate all active sessions via force logout;
             write audit_log entry: action: 'auto_deactivated', reason: 'employee_terminated'.
  Mechanism: Supabase DB trigger on employee_directory.status update OR event via
             internal message bus.

INT-UM-02  Onboarding → User Management
  Trigger  : Onboarding "Enable System Access" step completed for a new hire.
  Action   : Create app_users record (or link existing pending record) with role =
             'Employee'; send invitation email with welcome message.
  Mechanism: Onboarding app calls POST /api/user-management/provision-from-onboarding
             with employee_id payload.

INT-UM-03  User Management → All Apps
  Trigger  : User deactivated or deleted.
  Action   : All active sessions terminated (force logout); all pending push
             notification subscriptions for that user removed from Web Push VAPID
             subscriber list; active workflow tasks assigned to user flagged for
             reassignment.
  Mechanism: On status change, emit internal event 'user.deactivated' consumed by
             each app's subscription service.

INT-UM-04  Recruitment → User Management
  Trigger  : Candidate status set to 'Hired' AND 'Enable Access' confirmed by HR.
  Action   : Auto-create app_users record with role = 'Employee', linked by email;
             send invitation email.
  Mechanism: Recruitment app calls POST /api/user-management/provision-from-recruitment.

  Event    : Role changed.

NOTIF-UM-03

  Recipients: Affected user.

  Admin Message : "{userName} logged in from an unrecognised device/location:

NOTIF-UM-05
  Event    : Password reset requested.
  Recipients: Affected user.
  Type     : Action Required.
  Message  : "A password reset has been requested for your account. Check your

NOTIF-UM-06
  Event    : MFA enrollment required (role enforce_mfa enabled for user's role).

D6.2.1  OKR Tracking (New Tab)
---------------------------------------
  OKR Hierarchy:
    Company OKRs  → Department OKRs  → Individual OKRs
    Individual OKRs can optionally be linked (aligned) to a parent Department or
    Company OKR via parent_okr_id FK.

  Objective record (performance_okrs):
    title         — Clear, aspirational statement.
    description   — Optional elaboration.
    owner         — FK to app_users.id (individual) or department_id (dept-level).
    type          — 'Company' | 'Department' | 'Individual'
    time_period   — FK to review_cycle or free text (e.g. "Q3 2026").
    status        — 'On Track' | 'At Risk' | 'Behind' | 'Completed'
    parent_okr_id — FK → performance_okrs.id (nullable; for alignment).

  Key Result record (performance_key_results):
    title         — Measurable outcome description.
    target_value  — Numeric target (must be > 0).
    current_value — Latest check-in value (updated weekly).
    unit          — Unit label: %, ms, $, count, etc.
    due_date      — Deadline for this key result.
    status        — 'On Track' | 'At Risk' | 'Behind' | 'Completed'
    progress_%    — Computed: (current_value / target_value) * 100.

  Progress calculation:
    - Objective progress % = average of all child key result progress %.
    - Status auto-suggested based on progress vs time elapsed:
        > 70% of expected progress → On Track
        50–70% → At Risk
        < 50%  → Behind
        100%   → Completed
    - Owner can override status with a written reason.

  Weekly Check-In (required):
    - On Monday, push notification sent to each OKR owner.
    - Check-in form: update current_value for each key result + optional notes.
    - If no check-in submitted by Wednesday: second reminder notification.
    - OKRs with no check-in for >14 days flagged "Stale" in amber.

  - performance_feedback_requests: SELECT for requested_by, reviewee_id, reviewer_id,
    HR Manager, Admin. INSERT for HR Manager and Manager roles only.
  - performance_continuous_feedback: SELECT for giver_id, receiver_id, and
    receiver's manager and HR. INSERT for any authenticated user (self).
  - performance_pips: SELECT for employee (own PIP), their manager, HR Manager,
    Admin. INSERT/UPDATE for manager and HR Manager only.


--------------------------------------------------------------------------------
D6.4  VALIDATION RULES
--------------------------------------------------------------------------------

V-PT-01  Self-assessment: submission deadline enforced server-side (check
         review_cycle.self_assessment_deadline >= NOW() on submit endpoint).
         Returns HTTP 400: "Self-assessment deadline has passed."
         Cannot edit after self_assessment_locked = true.
         All competency ratings must be filled; evidence min 50 chars each;
         overall summary min 100 chars.

V-PT-02  Review rating: performance_reviews.manager_rating IS NOT NULL is required
         for each employee in the cycle before [Finalize Cycle] is permitted.
         calibrated_rating IS NOT NULL also required (can equal manager_rating if
         no calibration change made).

V-PT-03  360 Feedback request: min 2 peer reviewers required (reject if
         peer reviewer count < 2). Deadline must be >= today + 7 days (reject
         earlier dates). Cannot create a duplicate request:
         UNIQUE constraint on (cycle_id, reviewee_id, reviewer_id) prevents
         duplicate reviewer assignments for the same cycle.

V-PT-04  Calibration finalize: ALL employees in the cycle must have a
         non-null calibrated_rating. Server-side: COUNT(*) WHERE calibrated_rating
         IS NULL must equal 0. If not, return HTTP 409 with list of employee names
         pending calibration.

V-PT-05  PIP dates: start_date >= today (no backdating PIPs). end_date must be
         > start_date + 30 days (minimum 30-day PIP period). Milestone due_dates
         must be within the PIP start_date–end_date range.

V-PT-06  OKR: each Objective must have at least 1 Key Result before it can be
         published (status ≠ 'draft'). key_result.target_value > 0 enforced by
         DB CHECK constraint. Individual OKR owner must be an active employee.

V-PT-07  Continuous feedback self-feedback: giver_id ≠ receiver_id enforced
         server-side (HTTP 400: "You cannot submit feedback for yourself.").

V-PT-08  PIP closure: outcome must be provided; closure_notes required (min 20
         chars); hr_signoff_by must be a user with HR Manager or Admin role.

V-PT-09  OKR weekly check-in: if last_checkin_at < NOW() - interval '14 days',
         OKR is flagged 'Stale' in the application layer (no DB change; computed
         client-side or via server view).

V-PT-10  Performance cycle: cannot open a new review cycle for a department/group
         if there is an existing cycle in status 'in_progress' for the same
         group. Prevents overlapping active cycles.


--------------------------------------------------------------------------------
D6.5  CROSS-APP INTEGRATIONS
--------------------------------------------------------------------------------

INT-PT-01  Performance → Training
  Trigger  : performance_reviews.skill_gap_notes IS NOT NULL after manager review
             submission.
  Action   : Training app receives POST /api/training/suggest-courses with payload:
             { employee_id, skill_gap_notes, role_id }. Training app returns and
             displays suggested course cards in Performance review detail.
  Display  : "Suggested Training" section in review detail slide-over showing
             course name, duration, and [Enrol] button linking to Training app.

INT-PT-02  Performance → Workflow
  Trigger  : PIP creation (POST to performance_pips).
  Action   : Before employee notification, create an approval workflow task
             in the Workflow app: approver = HR Manager (derived from department).
             PIP status = 'pending_approval' until workflow approved.
             On approval: status → 'active'; trigger NOTIF-PT-04.
             On rejection: status → 'rejected'; manager notified with comments.

INT-PT-03  Performance → Employee Directory
  Trigger  : Review cycle finalized (status set to 'finalized').
  Action   : For each finalized review, write to employee_directory:
               last_review_cycle    = cycle name
               last_review_rating   = calibrated_rating
               competency_scores    = performance_reviews.competency_scores (JSONB)
               last_reviewed_at     = cycle finalize timestamp
  Mechanism: Supabase DB function called on cycle finalize endpoint.

INT-PT-04  Performance → Communications
  Trigger  : Continuous feedback submitted with type = 'Recognition' AND
             receiver's consent_share_recognition = true.
  Action   : POST to Communications Hub API: create feed item of type 'recognition'
             with: sender name, receiver name, recognition message (derived from
             SBI fields), timestamp.
  Display  : Appears as a card in the Communications Hub "Recognitions" section.

INT-PT-05  Performance → Notifications (Bell)
  All performance events route through the central Notifications service.
  All push notifications use Web Push API (VAPID).

D6.6  PUSH NOTIFICATIONS
--------------------------------------------------------------------------------

NOTIF-PT-01
  Event    : Review cycle opened.
  Recipients: All employees in the cycle.
  Type     : Action Required.
  Message  : "Your {cycleName} performance review is now open. Self-assessment
              is due by {deadline}."

NOTIF-PT-02
  Event    : Self-assessment deadline 3 days away; self_assessment_locked = false.
  Recipients: Employees in cycle who have NOT submitted (self_assessment_data IS NULL).
  Type     : Warning.
  Message  : "Reminder: Your self-assessment for {cycleName} is due in 3 days
              ({deadline})."

NOTIF-PT-03
  Event    : Self-assessment deadline passed without submission.
  Recipients: Non-submitting employees + their manager.
  Type     : Urgent.
  Message  : Employee: "Your self-assessment deadline has passed. Contact your
              manager or HR immediately."
             Manager: "{employeeName} has not submitted their self-assessment
              for {cycleName}. The deadline has passed."

NOTIF-PT-04
  Event    : PIP created and approved (workflow approved, status → 'active').
  Recipients: Employee (Action Required) + HR Manager (Action Required).
  Type     : Action Required.
  Employee message : "A Performance Improvement Plan has been created for you.
                      Review the details and milestones in the HR Portal."
  HR message       : "PIP for {employeeName} is now active and requires your
                      ongoing oversight."

NOTIF-PT-05
  Event    : PIP milestone due tomorrow.
  Recipients: Employee + their manager.
  Type     : Warning.
  Message  : "PIP milestone '{milestoneTitle}' for {employeeName} is due tomorrow.
              Log a check-in to record status."

NOTIF-PT-06
  Event    : PIP milestone missed (due_date passed, status still 'Pending').
  Recipients: HR Manager + senior manager (manager's manager).
  Type     : Warning.
  Message  : "PIP milestone '{milestoneTitle}' for {employeeName} has been missed.
              The PIP has been escalated."

NOTIF-PT-07
  Event    : 360 feedback request received.
  Recipients: Reviewer (person asked to give feedback).
  Type     : Action Required.
  Message  : "You have been asked to provide 360 feedback for {revieweeName}.
              Deadline: {deadline}. Click to submit feedback."

NOTIF-PT-08
  Event    : 360 feedback deadline 2 days away; reviewer has not submitted.
  Recipients: Reviewer.
  Type     : Warning.
  Message  : "Reminder: Your feedback for {revieweeName} is due in 2 days
              ({deadline})."

NOTIF-PT-09
  Event    : Manager review submitted for employee.
  Recipients: Employee.
  Type     : Info.
  Message  : "Your manager has submitted your {cycleName} performance review.
              View your review once the calibration period ends."

NOTIF-PT-10
  Event    : Review cycle finalized.
  Recipients: All reviewed employees.
  Type     : Info.
  Message  : "Your {cycleName} performance review has been finalised. You can
              now view your results in the HR Portal."

NOTIF-PT-11
  Event    : OKR weekly check-in due (Monday morning, cron-triggered).
  Recipients: OKR owners with OKRs in current active cycle.
  Type     : Info.
  Message  : "Weekly OKR check-in due. Update your key result values for this
              week to keep your progress current."

NOTIF-PT-12
  Event    : Recognition received (continuous feedback, type = Recognition).
  Recipients: Feedback receiver.
  Type     : Success.
  Message  : "{giverName} recognised you: '{situationExcerpt}'"
