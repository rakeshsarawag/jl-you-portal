SECTION 1 — WORKFLOW AUTOMATION: NEW TRIGGER EVENTS
================================================================================

OVERVIEW
--------
The existing workflow engine already supports:
  - Triggers   : manual | schedule | event
  - Node types : approval | notification | email | condition | delay |
                 parallel | create_record | update_field | webhook | loop

The following new trigger events are to be added to the
WORKFLOW_TRIGGER_EVENTS master data table.

TEMPLATE 8 — Invoice Overdue Reminder Workflow
--------------------------------------------------------------------------------
Trigger Event  : invoice_overdue
Trigger Type   : event (auto-trigger on event fire)
Purpose        : Automated multi-stage payment reminder to client with internal
                 finance escalation if the invoice remains unpaid

Node Sequence  :
  Node 1  | Type: delay
            Delay: 0 days (executes immediately on trigger)
            Purpose: Entry point — no initial hold

  Node 2  | Type: email
            To: {{client_email}}  (resolved from invoice client record)
            Subject: "Payment Reminder: Invoice {{invoice_number}} Overdue"
            Body: |
              Dear {{client_name}},

              This is a reminder that Invoice {{invoice_number}} is currently
              {{overdue_days}} days past its due date, with ₹{{balance_due}}
              outstanding.

              Please arrange payment at your earliest convenience to avoid
              further follow-up.

              Regards,
              Finance Team

  Node 3  | Type: notification
            To role: finance
            Message: "Invoice overdue reminder sent to {{client_name}} for
                      Invoice {{invoice_number}} (₹{{balance_due}} outstanding,
                      {{overdue_days}} days overdue)."

  Node 4  | Type: delay
            Delay: 7 days

  Node 5  | Type: condition
            Field: invoices.status  (re-fetched at runtime)
            Operator: not_equals
            Value: "paid"
            Branches: YES (still unpaid) → Node 6 | NO (paid) → end

  Node 6  | Type: email
            To: {{client_email}}
            Subject: "SECOND REMINDER: Invoice {{invoice_number}} — Immediate Payment Required"
            Body: |
              Dear {{client_name}},

              Despite our earlier reminder, Invoice {{invoice_number}} remains
              unpaid ({{overdue_days + 7}} days overdue). The outstanding amount
              is ₹{{balance_due}}.

              Continued non-payment may result in service suspension. Please
              contact us immediately if you have any queries.

              Regards,
              Finance Team

  Node 7  | Type: notification
            To roles: finance, admin
            Message: "ALERT: Invoice {{invoice_number}} for {{client_name}} is
                      still unpaid after 2 reminders (₹{{balance_due}} overdue).
                      Manual follow-up required."
            Priority: high

TEMPLATE 9 — Salary Revision Approval Workflow
--------------------------------------------------------------------------------
Trigger Event  : salary_revision_submitted
Trigger Type   : event (auto-trigger)
Purpose        : Route new salary revision records through HR Manager approval,
                 with notifications to relevant parties on resolution

Node Sequence  :
  Node 1  | Type: approval
            Approver role: hr_manager
            Response deadline: 48 hours
            On timeout: escalate to next role (admin / hr_head)
            Approval message: |
              "Salary revision submitted for {{employee_name}}:
               Current CTC: ₹{{old_ctc}}
               Proposed CTC: ₹{{new_ctc}}
               Effective From: {{effective_from}}
               Submitted By: {{submitted_by_name}}
               Please review and approve or reject."

  --- ON APPROVE BRANCH ---

  Node 2A | Type: update_field
            Table: salary_revision_history
            Record: {{revision_id}}
            Field: status
            Value: "approved"

  Node 2B | Type: notification
            To: {{employee_id}}
            Message: "Your salary has been revised to ₹{{new_ctc}} effective
                      {{effective_from}}. Your updated payslip will reflect this
                      change from the next payroll cycle."
            Priority: normal

  Node 2C | Type: notification
            To role: hr
            Message: "Salary revision approved for {{employee_name}} —
                      CTC updated from ₹{{old_ctc}} to ₹{{new_ctc}}."

  --- ON REJECT BRANCH ---

  Node 2D | Type: notification
            To: {{submitted_by}}
            Message: "Salary revision for {{employee_name}} has been rejected.
                      Reason: {{rejection_reason}}. Please review and resubmit
                      if required."
            Priority: normal

TEMPLATE 10 — OKR Check-In Reminder Workflow
--------------------------------------------------------------------------------
Trigger Type   : schedule
Schedule       : Every Monday at 08:00 (system timezone)
Purpose        : Ensure OKR owners complete weekly check-ins; escalate to
                 manager if ignored through mid-week

Node Sequence  :
  Node 1  | Type: (server-side query / loop)
            Action: Query all employees with active OKRs in current cycle
                    where last_checkin_date < Monday of this week
            Output: list of {employee_id, okr_id, manager_id, employee_name}
            Note: Implemented as a scheduled Supabase Edge Function that
                  fires each Monday and dispatches per-employee workflow runs

  Node 2  | Type: email
            To: {{employee_email}}
            Subject: "Weekly OKR Check-In Due — Q{{quarter}} {{year}}"
            Body: |
              Hi {{employee_name}},

              Your weekly OKR progress check-in is due for Q{{quarter}}.
              Keeping your check-ins up to date helps your team stay aligned
              and surfaces blockers early.

              Please log your progress in the OKR portal at your earliest
              convenience.

  Node 3  | Type: notification
            To: {{employee_id}}
            Message: "Your weekly OKR check-in is due. Please update your
                      progress for Q{{quarter}}."
            Priority: normal

  Node 4  | Type: delay
            Delay: 2 days (Wednesday)

  Node 5  | Type: condition
            Check: okr check-in for this week still not recorded?
            (Re-query okr_checkins for current week)
            Branches: YES (not done) → Node 6 | NO (done) → end

  Node 6  | Type: notification
            To: {{manager_id}}
            Message: "{{employee_name}} has not completed their OKR check-in
                      for this week. You may want to follow up directly."
            Priority: normal

TEMPLATE 11 — Payroll Processing Reminder Workflow
--------------------------------------------------------------------------------
Trigger Type   : schedule
Schedule       : 3 days before each month's configured processing_day
                 (resolved dynamically from payroll_settings.processing_day)
Purpose        : Remind Finance Manager to ensure all payroll prerequisites
                 (salary structures, attendance) are in order before run

Node Sequence  :
  Node 1  | Type: notification
            To role: finance_manager
            Message: "Payroll processing for {{month_name}} {{year}} is
                      scheduled for the {{processing_day}}th. Please ensure
                      all salary structures and attendance records are updated
                      before processing."
            Priority: high

  Node 2  | Type: email
            To: {{finance_manager_email}}
            Subject: "Action Required: {{month_name}} Payroll Processing Due on {{processing_day}}th"
            Body: |
              Hi {{finance_manager_name}},

              This is your 3-day advance notice that payroll processing for
              {{month_name}} {{year}} is due on the {{processing_day}}th.

              Before processing, please verify:
                - All salary structures are finalised
                - Attendance and leave records are up to date
                - Any salary revisions approved this month are reflected
                - Statutory deductions (PF, ESI, TDS) are configured correctly

              Please process payroll on time to ensure employees receive their
              payslips without delay.

  Node 3  | Type: delay
            Delay: until processing_day - 1 day (dynamic, computed at runtime)

  Node 4  | Type: condition
            Check: payroll for current month still not in "processed" or
                   "finalized" status?
            Branches: YES (not processed) → Node 5 | NO (done) → end

  Node 5  | Type: notification
            To roles: finance_manager, hr_manager
            Message: "URGENT: Payroll for {{month_name}} {{year}} has not
                      been processed and is due tomorrow ({{processing_day}}th).
                      Immediate action required."
            Priority: urgent

TEMPLATE 13 — Analytics Anomaly Escalation Workflow
--------------------------------------------------------------------------------
Trigger Event  : anomaly_detected  (severity = high only)
Trigger Type   : event (auto-trigger, filtered by severity)
Purpose        : Alert analytics admins of high-severity metric anomalies;
                 require acknowledgment; escalate to C-suite if unresolved

Filter Condition (pre-trigger) : payload.severity IN ("high", "critical")

Node Sequence  :
  Node 1  | Type: condition
            Check: deviation_percent > 20%?
            Branches: YES (major anomaly) → Node 2A | NO (minor high) → Node 2B

  Node 2A | Type: approval
            Approver role: analytics_admin
            Message: "Anomaly detected in metric '{{metric_key}}':
                      {{deviation_percent}}% deviation from baseline
                      (Current: {{current_value}} | Baseline: {{baseline_value}}).
                      Please review and acknowledge this alert."
            Timeout: 24 hours → auto-escalate

  Node 2B | Type: notification
            To role: analytics_admin
            Message: "Info: Metric '{{metric_key}}' shows {{deviation_percent}}%
                      deviation (current: {{current_value}}, baseline:
                      {{baseline_value}}). Monitoring."
            Priority: low
            (Workflow ends here for this branch)

  Node 3  | Type: delay
            Delay: until acknowledged OR 24 hours (whichever first)

  Node 4  | Type: condition
            Check: anomaly still active / unresolved?
            Branches: YES (still anomalous) → Node 5 | NO (resolved) → end

  Node 5  | Type: notification
            To roles: admin, c_suite
            Message: "ESCALATION: Anomaly in '{{metric_key}}' remains unresolved
                      after 24 hours. {{deviation_percent}}% deviation. Executive
                      review recommended."
            Priority: urgent
            Web Push: true

TEMPLATE 14 — Security Breach Alert Workflow
--------------------------------------------------------------------------------
Trigger Event  : critical_audit_event
Trigger Type   : event (auto-trigger, severity = critical only)
Purpose        : Immediate parallel alert to security stakeholders; escalate
                 to all admins and C-suite if not resolved within 1 hour

Filter Condition (pre-trigger) : payload.severity = "critical"

Node Sequence  :
  Node 1  | Type: parallel
            Execute branches simultaneously:

            Branch A:
              Type: notification
              To roles: admin, security
              Message: "CRITICAL SECURITY EVENT: {{action}} by {{user_email}}
                        on resource '{{resource}}' from IP {{ip_address}}.
                        Immediate investigation required."
              Priority: urgent
              Web Push: true (bypass quiet hours)

            Branch B:
              Type: email
              To: {{it_admin_email}}, {{ciso_email}}
              Subject: "CRITICAL SECURITY ALERT — Immediate Action Required"
              Body: |
                A critical security event has been detected:

                  User     : {{user_email}}
                  Action   : {{action}}
                  Resource : {{resource}}
                  IP       : {{ip_address}}
                  Timestamp: {{event_timestamp}}

                Please investigate immediately and take appropriate action.
                Log into the Security & Compliance module to review the full
                audit trail.

  Node 2  | Type: delay
            Delay: 1 hour

  Node 3  | Type: condition
            Check: security event resolved/acknowledged?
                   (audit_log record marked as reviewed = true)
            Branches: YES (resolved) → end | NO → Node 4

  Node 4  | Type: notification
            To roles: admin, c_suite
            Message: "ESCALATION: Critical security event from 1 hour ago
                      remains unacknowledged. User: {{user_email}} |
                      Action: {{action}} | IP: {{ip_address}}.
                      All administrators notified."
            Priority: urgent
            Web Push: true (bypass quiet hours, forced delivery)

Event Key                    | Template                             | Mode

  - invoice_overdue_14d fires when a separate DB check confirms 14+ days;
    it routes into the same template at Node 6 (second reminder) rather than
    restarting from Node 1

--------------------------------------------------------------------------------
3.2  WORKFLOW → APP WRITE INTEGRATIONS
--------------------------------------------------------------------------------

Workflow → Invoice:
  - create_record_node: can create an invoice record and mark it as "sent"
  - update_field_node: can update invoices.status to "paid", "cancelled", etc.

Workflow → Payroll:
  - Approval step resolves salary_revision_history.status
  - Notification nodes fire for payroll processing and lock events

Workflow → OKR:
  - Notification nodes send check-in reminders to OKR owners
  - Notification nodes escalate blocker events to assigned managers

Workflow → Security:
  - New node type: audit_log_node
    Writes a record to audit_logs when a workflow node executes.
    Fields written: action="workflow_node_executed", resource="workflow:{workflow_id}",
                    user_id="system", severity="info", metadata={node_type, workflow_run_id}
    Useful for compliance trails of automated actions.

Workflow → Analytics:
  - webhook_node can call the analytics aggregation endpoint to invalidate
    or refresh a specific metric cache after a workflow modifies underlying data
    Endpoint pattern: POST /api/analytics/refresh  body: {metric_key}

--------------------------------------------------------------------------------
3.3  NEW NODE TYPE SPECIFICATION: audit_log_node
--------------------------------------------------------------------------------

Node Type     : audit_log_node
Category      : Action
Description   : Writes a structured record to the audit_logs table, enabling
                workflows to leave a compliance-grade paper trail

Configuration Fields:
  action      : string (required) — e.g. "payroll_approved", "invoice_reminded"
  resource    : string (optional) — table or entity reference
  severity    : enum: info | low | medium | high | critical  (default: info)
  metadata    : object (optional) — arbitrary key/value pairs to persist

Runtime Behavior:
  - Writes to audit_logs with user_id = "system (workflow)"
  - Does not block workflow execution (fire-and-forget insert)
  - On insert failure: logs warning to workflow_run_errors, does not halt run

UI in Workflow Builder:
  - Displayed in node palette under "Actions" category
  - Icon: shield with checkmark
  - Color accent: green (#22c55e)

Implementation Note on "Forced-On":
  The notification_preferences table stores user overrides. Forced-on events
  are evaluated at delivery time: if the event is in the forced_events set
  for the user's role, the stored preference is ignored and delivery always
  proceeds. The UI reflects this by rendering the toggle as locked regardless
  of stored value.

  Supabase table: forced_notification_events
    Columns: event_key (text), role (text), channel (text: "in_app" | "push")
    Primary Key: (event_key, role, channel)
    Populated at migration time; not user-editable.
