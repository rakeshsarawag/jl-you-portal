G1 — HR Admin Encashment View
--------------------------------------------------------------------------------
Problem:
  Approvals tab currently shows only direct-reports' encashment requests.
  HR Admins need visibility into ALL employees' encashment requests.

Fix:
  Add an "Encashment" sub-tab inside the Approvals tab, visible only when the
  logged-in user has role = HR_ADMIN or SUPER_ADMIN.

  The sub-tab queries without a userId filter:
    GET /employee-dashboard/leave-encashments
      Query params: status (optional), department (optional), page, limit
    For manager role:
      GET /employee-dashboard/leave-encashments?managerId={userId}
    For HR_ADMIN / SUPER_ADMIN:
      GET /employee-dashboard/leave-encashments
      (no userId or managerId filter — returns all)

  Backend must enforce this via the Permissions App role check on the endpoint;
  non-admin callers without a managerId param receive 403.

No new DB tables required. Existing leave_encashments table is used.
Add index on leave_encashments(status) if not present.

G2 — Shift Schedule Tab
--------------------------------------------------------------------------------
New DB Table — employee_shifts:
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid()
  employee_id     uuid NOT NULL REFERENCES employees(id)
  shift_id        uuid NOT NULL REFERENCES shifts(id)
  effective_from  date NOT NULL
  effective_to    date                          -- NULL = open-ended (current)
  created_by      uuid REFERENCES employees(id)
  created_at      timestamptz DEFAULT now()
  updated_at      timestamptz DEFAULT now()

  Index: (employee_id, effective_from DESC)
  RLS: employee can SELECT own rows; manager can SELECT team rows; HR can SELECT all.

New DB Table — shifts (if not already in Master Data):
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid()
  name        text NOT NULL          -- e.g. "General", "Morning", "Night"
  start_time  time NOT NULL          -- e.g. 09:00
  end_time    time NOT NULL          -- e.g. 18:00
  type        text                   -- GENERAL | MORNING | EVENING | NIGHT | ROTATIONAL
  color_hex   text                   -- for UI color-coding, e.g. #6366F1
  is_active   boolean DEFAULT true
  created_at  timestamptz DEFAULT now()

New DB Table — shift_swap_requests:
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid()
  requester_id    uuid NOT NULL REFERENCES employees(id)
  swap_with_id    uuid NOT NULL REFERENCES employees(id)
  requester_date  date NOT NULL
  swap_date       date NOT NULL
  reason          text NOT NULL
  status          text DEFAULT 'Pending'   -- Pending | Approved | Rejected
  manager_notified_at timestamptz
  reviewed_by     uuid REFERENCES employees(id)
  reviewed_at     timestamptz
  created_at      timestamptz DEFAULT now()
  updated_at      timestamptz DEFAULT now()

New API Endpoints:
  GET  /attendance/shifts/{userId}
       Returns: array of { shift, effective_from, effective_to }
       Scope: own record for employee; team for manager; all for HR.

  GET  /attendance/shifts/{userId}/weekly?week={YYYY-WNN}
       Returns: 7-element array, one per day, with shift assignment per day.

  GET  /attendance/shifts/{userId}/monthly?month={YYYY-MM}
       Returns: array of { date, shift } for the month.

  POST /attendance/shift-swap-request
       Body: { swap_with_id, requester_date, swap_date, reason }
       Returns: created shift_swap_request record.

  GET  /attendance/shift-swap-requests/{userId}
       Returns: requests where requester_id = userId OR swap_with_id = userId.

  PATCH /attendance/shift-swap-requests/{id}
       Body: { status: "Approved" | "Rejected", comment? }
       Restricted to: swap_with_id (peer approval) and manager (final sign-off).

G3 — Payslip Tab
--------------------------------------------------------------------------------
New DB Table — payslips:
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid()
  employee_id    uuid NOT NULL REFERENCES employees(id)
  month          integer NOT NULL       -- 1–12
  year           integer NOT NULL
  gross          numeric(12,2) NOT NULL
  deductions     numeric(12,2) NOT NULL
  net            numeric(12,2) NOT NULL
  pdf_url        text                   -- signed URL or storage path
  earnings_json  jsonb                  -- { basic, hra, special, bonus, arrears }
  deductions_json jsonb                 -- { pf, prof_tax, tds, lop_deduction }
  created_at     timestamptz DEFAULT now()

  Unique constraint: (employee_id, month, year)
  RLS: employee can SELECT own rows only; Finance/HR role can SELECT all.
  Note: payslip data is INSERT/UPDATE only by Finance app or payroll integration.
        Employee Dashboard is read-only on this table.

New API Endpoints:
  GET /payslips/{userId}
      Returns: list of available payslip month/year pairs (for dropdown).

  GET /payslips/{userId}/{year}/{month}
      Returns: full payslip record including earnings_json and deductions_json.

  GET /payslips/{userId}/{year}/{month}/pdf
      Returns: { pdf_url: "<signed URL>" } (URL valid for 15 minutes).
      Backend generates a fresh signed URL from storage on each request.

G4 — Team Calendar Permission Scoping
--------------------------------------------------------------------------------
Problem:
  Team Calendar tab is hidden for non-manager roles.

Fix:
  Make Team Calendar tab visible to ALL authenticated employees.
  Scope data server-side based on role:

  Employee (role = EMPLOYEE):
    GET /team-calendar?userId={id}&scope=self
    Returns only the requesting employee's own approved leaves, WFH records,
    and public holidays.

  Manager (role = MANAGER or TEAM_LEAD):
    GET /team-calendar?managerId={id}&scope=team
    Returns all direct reports' leaves, WFH, and public holidays.

  HR / Super Admin:
    GET /team-calendar?scope=all&department={dept}  (optional dept filter)
    Returns all employees' leaves, WFH, and public holidays.

  Frontend: render "Filter by employee" dropdown only when role >= MANAGER.
  Color coding:
    Blue chip  = Approved Leave
    Orange chip = WFH (approved)
    Gray chip  = Public Holiday
  Employee name on chip is shown only in manager / HR view.

No schema changes required. Endpoint behavior changes only.

G5 — Attendance Regularization
--------------------------------------------------------------------------------
New DB Table — attendance_corrections:
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid()
  employee_id         uuid NOT NULL REFERENCES employees(id)
  date                date NOT NULL
  expected_checkin    time NOT NULL
  expected_checkout   time NOT NULL
  reason              text NOT NULL       -- min 20 chars enforced in backend
  status              text DEFAULT 'Pending'  -- Pending | Approved | Rejected
  reviewed_by         uuid REFERENCES employees(id)
  reviewed_at         timestamptz
  review_comment      text
  created_at          timestamptz DEFAULT now()
  updated_at          timestamptz DEFAULT now()

  Index: (employee_id, date)
  RLS: employee can SELECT/INSERT own rows; manager can SELECT team + PATCH status.

New API Endpoints:
  POST /attendance/correction-request
       Body: { date, expected_checkin, expected_checkout, reason }
       Validations (server-side):
         - date <= today
         - date >= first day of previous month
         - pending corrections for employee < 3
         - expected_checkin < expected_checkout
         - reason length >= 20
       Returns: created attendance_corrections record.

  GET  /attendance/corrections/{userId}
       Returns: all correction requests for userId.
       Scope: employee sees own; manager sees team.

  PATCH /attendance/corrections/{id}
       Body: { status: "Approved" | "Rejected", review_comment? }
       Restricted to direct manager of the employee.
       On Approved: updates attendance record for that date with expected times.

G6 — Comp-Off Tracking
--------------------------------------------------------------------------------
New DB Table — comp_off_requests:
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid()
  employee_id  uuid NOT NULL REFERENCES employees(id)
  worked_date  date NOT NULL
  reason       text NOT NULL
  is_holiday   boolean DEFAULT false
  hours        numeric(4,2) NOT NULL      -- hours worked (e.g. 8.0)
  status       text DEFAULT 'Pending'    -- Pending | Approved | Rejected
  approved_by  uuid REFERENCES employees(id)
  approved_at  timestamptz
  expires_at   date                       -- worked_date + 90 days, set on approval
  created_at   timestamptz DEFAULT now()
  updated_at   timestamptz DEFAULT now()

  Index: (employee_id, status)
  RLS: employee can SELECT/INSERT own rows; manager can SELECT team + PATCH.

New API Endpoints:
  POST /leaves/comp-off-request
       Body: { worked_date, reason, is_holiday, hours }
       Validations:
         - worked_date must be a Saturday, Sunday, or a public holiday
         - worked_date >= today - 7 days (submission within 7 days)
         - pending comp-off requests < 3
       Returns: created comp_off_requests record.

  GET  /leaves/comp-off-requests/{userId}
       Returns: all comp-off requests for userId with status and expiry.

  PATCH /leaves/comp-off-requests/{id}
       Body: { status: "Approved" | "Rejected", comment? }
       On Approved:
         - Sets expires_at = worked_date + 90 days
         - POSTs to leave_balances: increments Comp Off balance by (hours / 8) days
         - Triggers push notification: compoff_approved

Expiry Handling:
  A scheduled function (cron, daily at midnight) checks comp_off_requests where
  status = Approved and expires_at <= today and leave_balances.comp_off > 0,
  then decrements the balance and marks the comp-off as expired.

G7 — WFH Approval Workflow (Replace Self-Toggle)
--------------------------------------------------------------------------------
Remove:
  - WFH self-service toggle button from Overview tab.

New DB Table — wfh_requests:
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid()
  employee_id  uuid NOT NULL REFERENCES employees(id)
  date         date NOT NULL
  reason       text NOT NULL
  available_on_call boolean DEFAULT true
  status       text DEFAULT 'Pending'    -- Pending | Approved | Rejected
  approved_by  uuid REFERENCES employees(id)
  approved_at  timestamptz
  reject_reason text
  created_at   timestamptz DEFAULT now()
  updated_at   timestamptz DEFAULT now()

  Unique constraint: (employee_id, date)
  RLS: employee can SELECT/INSERT own rows; manager can SELECT team + PATCH.

New API Endpoints:
  POST /attendance/wfh-request
       Body: { date, reason, available_on_call }
       Validations:
         - date >= today + WFH_POLICIES.advance_notice_hours / 24
         - date is not a public holiday
         - WFH days this week < WFH_POLICIES.max_wfh_days_per_week
       Returns: created wfh_requests record.

  GET  /attendance/wfh-requests/{userId}
       Returns: all WFH requests for userId.

  PATCH /attendance/wfh-requests/{id}
       Body: { status: "Approved" | "Rejected", reject_reason? }
       On Approved: creates an attendance record for that date with type = WFH.

Master Data Config (WFH_POLICIES):
  advance_notice_hours    integer  DEFAULT 24
  max_wfh_days_per_week   integer  DEFAULT 2

SECTION 4 — VALIDATION RULES
================================================================================

Leave Application:
  - start_date <= end_date
  - start_date cannot be a public holiday (warn user; exclude holidays from day count)
  - minimum notice days: from LEAVE_TYPES[type].min_notice_days config
  - maximum continuous days: from LEAVE_TYPES[type].max_continuous_days config
  - balance check: if requested days > available balance:
      warn "Insufficient balance — this will create {N} LOP days"
      user must confirm to proceed with LOP
  - no overlapping with existing approved/pending leaves for same employee
  - half-day selection: only allowed when start_date = end_date
  - cannot apply leave for a date in the past (unless policy allows; check LEAVE_POLICIES)

WFH Request:
  - date >= today + CEIL(WFH_POLICIES.advance_notice_hours / 24) days
  - date is not a public holiday
  - WFH days in the same calendar week (Mon–Sun) < WFH_POLICIES.max_wfh_days_per_week
    (count approved + pending WFH for the week)
  - no duplicate WFH request for the same date

Attendance Regularization:
  - date <= today
  - date >= first day of the previous calendar month
  - expected_checkin (HH:MM) < expected_checkout (HH:MM)
  - reason.length >= 20 characters
  - count of status=Pending corrections for employee < 3
  - cannot regularize a date that already has an approved correction

Comp-Off Request:
  - worked_date must be a Saturday, Sunday, or a date in the public holidays list
  - today - worked_date <= 7 days (must submit within 7 days of the work date)
  - count of status=Pending comp-off requests < 3
  - hours > 0 and hours <= 24

Leave Encashment:
  - leave_balances[Earned Leave] >= LEAVE_POLICIES.min_encashable_balance
  - days_to_encash <= min(available_earned_leave, 10)
  - days_to_encash >= 1
  - after encashment: remaining balance >= LEAVE_POLICIES.min_balance_after_encashment
    (default = 0; configurable)

SECTION 5 — WORKFLOW AUTOMATION INTEGRATION
================================================================================

All workflow events are POSTed to the Workflow App event bus.
Workflow App handles routing, escalation timers, and SLA tracking.

--------------------------------------------------------------------------------
5.1 Leave Approval Workflow
--------------------------------------------------------------------------------
Trigger event: leave_applied
  Payload: { leave_id, employee_id, manager_id, leave_type, days, start_date, end_date }

Routing:
  Step 1: Route to direct manager (employees.manager_id) for approval.
  Step 2: If leave_days > 5: additional approval required from HR Manager.
             (HR Manager resolved via Permissions App: role=HR_MANAGER for department)

On Approval (all steps complete):
  - Update leaves record: status = Approved
  - Deduct from leave_balances: balance -= days (for the leave type)
  - Create attendance records for each leave day: type = leave_type
  - Push notification to employee: leave_approved

On Rejection (any step):
  - Update leaves record: status = Rejected, rejection_reason = comment
  - Push notification to employee: leave_rejected (with reason)

On Withdrawal (by employee before approval):
  - Update leaves record: status = Withdrawn
  - No balance change

--------------------------------------------------------------------------------
5.2 WFH Approval Workflow
--------------------------------------------------------------------------------
Trigger event: wfh_requested
  Payload: { wfh_id, employee_id, manager_id, date, reason }

Routing: single-step, direct manager only.

On Approval:
  - Update wfh_requests: status = Approved
  - Create/update attendance record for date: type = WFH
  - Push notification to employee: wfh_approved

On Rejection:
  - Update wfh_requests: status = Rejected, reject_reason = comment
  - Push notification to employee: wfh_rejected

--------------------------------------------------------------------------------
5.3 Attendance Regularization Workflow
--------------------------------------------------------------------------------
Trigger event: regularization_submitted
  Payload: { correction_id, employee_id, manager_id, date, expected_checkin, expected_checkout }

Routing: single-step, direct manager only.

On Approval:
  - Update attendance_corrections: status = Approved, reviewed_by, reviewed_at
  - Update attendance record for date: checkin = expected_checkin, checkout = expected_checkout,
    recalculate hours and status (Present / Late based on shift)
  - Push notification to employee: regularization_approved

On Rejection:
  - Update attendance_corrections: status = Rejected, review_comment
  - Push notification to employee: regularization_rejected (with comment)

--------------------------------------------------------------------------------
5.4 Comp-Off Approval Workflow
--------------------------------------------------------------------------------
Trigger event: compoff_submitted
  Payload: { compoff_id, employee_id, manager_id, worked_date, hours }

Routing: single-step, direct manager only.

On Approval:
  - Update comp_off_requests: status = Approved, approved_by, approved_at,
    expires_at = worked_date + 90 days
  - Update leave_balances: comp_off_balance += ROUND(hours / 8, 1) days
  - Push notification to employee: compoff_approved

On Rejection:
  - Update comp_off_requests: status = Rejected
  - Push notification to employee: compoff_rejected

SECTION 7 — CROSS-APP INTEGRATIONS
================================================================================

--------------------------------------------------------------------------------
7.1 Communications Hub → Employee Dashboard (read)
--------------------------------------------------------------------------------
Endpoint: GET /communications/announcements
  Query: limit=3, audience={employee's department code or "ALL"}
  Returns: [ { id, title, published_at, author, audience } ]
  Used in: Overview tab — Announcements card (right column)
  Fallback: if Communications app unavailable, hide Announcements card silently.

--------------------------------------------------------------------------------
7.2 Training App → Employee Dashboard (read)
--------------------------------------------------------------------------------
Endpoint: GET /training/enrollments
  Query: userId={id}, status=enrolled, upcoming=true, limit=3
  Returns: [ { course_id, course_name, due_date, status } ]
  Used in: Overview tab — Upcoming card (left column), training items
  Fallback: hide training items silently.

--------------------------------------------------------------------------------
7.3 Employee Dashboard → Workflow App (write / trigger)
--------------------------------------------------------------------------------
All approval workflows (leave, WFH, regularization, comp-off) publish events to:
  POST /workflow/events
  Body: { event_type, entity_id, entity_type, actor_id, payload }

Workflow App handles:
  - Routing to correct approver(s)
  - Escalation if no action within SLA (configurable, default 48h)
  - Multi-step sequences (e.g. leave > 5 days → manager → HR Manager)
  - Sending push notifications at each step

--------------------------------------------------------------------------------
7.4 Team Calendar Refresh on Leave Approval
--------------------------------------------------------------------------------
When a leave is approved:
  Workflow App publishes: leave_approved event.
  Team Calendar data cache is invalidated for:
    - The employee's calendar
    - The manager's team calendar
    - (For HR) all-employee calendar

  Frontend: Employee Dashboard subscribes to a Supabase Realtime channel
  (channel: team-calendar-updates) and refreshes Team Calendar data on event.

Implementation:
  Supabase Realtime broadcast channel: "team-calendar"
  Payload on leave approval: { type: "leave_approved", employee_id, leave_id }
  Frontend listener:
    supabase.channel("team-calendar")
      .on("broadcast", { event: "leave_approved" }, () => refetchTeamCalendar())
      .subscribe()

--------------------------------------------------------------------------------
7.5 Payslip — Finance App / Payroll Integration (read-only)
--------------------------------------------------------------------------------
Payslips data is owned by Finance App or an external payroll service.
Employee Dashboard has read-only access.

Options (choose based on architecture):
  Option A — Direct Supabase table access:
    Finance app writes to payslips table in same Supabase project.
    Employee Dashboard reads via Supabase client with RLS (employee sees own only).

  Option B — REST proxy:
    Finance App exposes: GET /payslips/{userId}/{year}/{month}
    Employee Dashboard backend acts as proxy, adds auth token.

  PDF Download:
    Regardless of option, PDF is stored in Supabase Storage (bucket: payslips).
    Employee Dashboard backend generates a signed URL on demand (15-minute expiry).
    Employee can download; URL is not stored in DB to prevent stale links.

Note:
  Employee Dashboard must never expose the raw Supabase Storage path.
  Always go through the backend signed URL endpoint.
